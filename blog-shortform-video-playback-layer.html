홈 캐러셀, 상품상세, 전체화면 숏폼을 하나의 :video 모듈로 묶은 설계

세로로 스와이프하며 영상 스무 개를 넘기는 화면을 만든다고 해봅시다. 그 화면에서 동시에 살아 있어야 하는 ExoPlayer 인스턴스는 몇 개일까요? 답을 정하고 읽어주세요.

양 극단은 각각 다른 곳에서 무너집니다. 하나만 두면 스와이프할 때마다 같은 인스턴스에 새 미디어를 붙이고 prepare() 를 다시 돌려야 하니, 사용자는 매번 첫 프레임을 기다립니다. 반대로 화면 수만큼 만들면 디코더가 버팁니다. media3 가 ERROR_CODE_DECODING_RESOURCES_RECLAIMED 라는 에러 코드를 따로 두고 그 뜻을 "higher priority task reclaiming resources needed for decoding" 이라고 적어 둔 것 자체가[1], 디코더 자원이 뺏길 수 있는 공유 자원이라는 뜻입니다. 버퍼 메모리도 인스턴스 수에 비례해서 늘어납니다.

컬리 앱에 동영상 커머스를 넣으면서 이 질문에 답해야 했습니다. 그것도 한 번이 아니라 세 번, 서로 요구가 다른 세 지면에서요. 이 글은 그 답을 :video 라는 모듈 하나로 모은 과정을 다룹니다.

이 변경의 규모

198개 파일, 12,692줄 추가. 신규 모듈 두 개(:video 3,308줄, :features:shortform 5,072줄)와 @Test 329개(PR diff 추가분 기준)가 함께 들어갔습니다. 아직 사용자에게 나가지 않은 상태(QA 진행 중)라, 이 글에는 운영 지표가 없습니다.

1. 지면은 셋인데 플레이어는 몇 개여야 하는가

영상이 붙는 자리는 세 곳입니다. 홈 추천탭의 가로 캐러셀, 상품상세의 연관 콘텐츠 줄, 그리고 세로 전체화면 플레이어입니다. 셋 다 "영상을 튼다"는 점만 같고 나머지는 전부 다릅니다.

재생 조건이 지면마다 다른 건 회수 방식이 다르기 때문입니다. 홈 캐러셀은 ComposeView 가 DisposeOnDetachedFromWindow 라, 화면 밖으로 리사이클되는 순간 컨트롤러가 통째로 폐기됩니다. 반면 상품상세 연관 콘텐츠는 같은 화면 안에서 스크롤만 되므로 아무것도 폐기되지 않아요. 그래서 이쪽에만 가시성 게이트(onVisibleFractionChanged)를 따로 달았습니다.

세 지면의 차이를 각 화면이 알아서 처리하게 두면, ExoPlayer 를 다루는 코드가 세 벌 생깁니다. 그래서 공통으로 묶을 수 있는 것을 아래로 내렸습니다. 인스턴스를 몇 개 만들지, 어떤 슬롯에 어떤 영상을 붙일지, 지금 이 슬롯의 상태가 무엇인지는 :video 가 혼자 결정합니다. 각 지면은 "지금 활성 항목은 이것" 이라고 알려주기만 해요.

멘탈 모델

실선 파란 상자만 지면이 직접 부릅니다. 점선은 이 글에서 깊이 다루지 않는 계층이고, internal 묶음 안쪽은 모듈 밖에서 이름조차 볼 수 없습니다. 겹쳐 그린 ExoPlayer 는 개수가 고정이 아니라는 뜻이에요.

2. :video 의 경계, 무엇을 안 넣었나

모듈을 새로 만들 때 제일 중요한 결정은 무엇을 넣을지가 아니라 무엇을 안 넣을지입니다. 의존성 선언이 그 결정을 그대로 보여줍니다.

:domain 이 없습니다. 이게 핵심입니다. 숏폼 도메인 모델인 ShortformRatio 를 :video 가 직접 받으면, 재생 계층이 숏폼이라는 특정 기능에 묶입니다. 그래서 :video 는 자기만의 VideoRatio 를 갖고, 변환은 한 층 위에서 합니다.

// features/core/ui/widget/.../video/VideoRatioMapper.kt
fun ShortformRatio.toVideoRatio(): VideoRatio {
    return when (this) {
        is ShortformRatio.Landscape -> VideoRatio.Landscape(value)
        is ShortformRatio.Portrait -> VideoRatio.Portrait(value)
        is ShortformRatio.Square -> VideoRatio.Square(value)
    }
}

같은 파일에 videoRatioOf(videoType: String?, videoAspect: Double?) 도 있습니다. 상품상세 연관 콘텐츠는 전용 도메인 타입을 거치지 않고 서버 문자열을 그대로 들고 오기 때문에, 문자열에서 바로 변환하는 경로가 따로 필요했어요. 이 중 videoRatioOf 는 알 수 없는 문자열을 세로형으로 봅니다. 숏폼 쪽 ShortformRatio.from 과 같은 규칙이에요. toVideoRatio 에는 그런 분기가 아예 없습니다. sealed 인터페이스를 받는 exhaustive when 이라 "알 수 없는 값" 이라는 경우가 존재할 수 없고, 폴백은 한 단계 위 도메인 변환에 있으니까요.

경계는 가시성으로도 한 번 더 잠급니다. VideoPool, VideoStateStore, VideoTickHandler, PageBinding, PlayerOwner, VideoDeviceProfile 은 전부 internal 입니다. 모듈 밖으로 나가는 것은 아래로 한정됩니다. VideoHandle 은 공개 클래스지만 생성자가 internal 이고, videoIndex 와 owner, generation 프로퍼티도 internal 입니다. 바깥에서는 만들 수도, 내부 좌표를 읽을 수도 없습니다 (itemId 만 공개입니다).

공개된 것이 적지는 않지만, 목록의 성격이 한쪽으로 쏠려 있습니다. 제어 표면과 값 타입과 Compose 연동뿐이고 재생 자원 자체는 하나도 없습니다. ExoPlayer 도, 풀도, 상태 저장소도 나가지 않아요.

호출자가 ExoPlayer 를 직접 만질 수 있으면 풀의 계약이 깨집니다. :video 가 ExoPlayer 를 반환하는 유일한 지점은 PlayerOwner.playerFor(handle) 이고, 이건 internal 입니다. 그래서 실제로 플레이어를 받아 쓰는 곳은 같은 모듈 안의 VideoSurface 하나뿐입니다.

3. 인스턴스 풀과 슬라이딩 창

풀의 규칙은 한 문장입니다. 활성 인덱스 주변만 붙들고, 나머지는 놓는다. 그 "주변" 을 계산하는 코드가 VideoPoolWindow 인데, 파일 전체가 스무 줄 남짓입니다.

internal object VideoPoolWindow {

    fun keepIndices(active: Int, size: Int, poolSize: Int): Set<Int> {
        if (size <= 0 || poolSize <= 0) return emptySet()
        val clampedActive = active.coerceIn(0, size - 1)
        val backward = (poolSize - 1) / 2
        val forward = poolSize / 2
        return (clampedActive - backward..clampedActive + forward)
            .filter { it in 0 until size }
            .toSet()
    }
}

backward 와 forward 를 다르게 나눈 게 이 함수의 전부입니다. 풀 크기가 짝수면 앞뒤로 똑같이 나눌 수 없는데, 이때 뒤쪽(다음 영상)을 한 칸 더 가져갑니다. 사용자가 주로 아래로 넘기니까 다음 영상을 미리 버퍼링해 두는 가치가 더 크거든요.

풀 크기 3일 때 활성 인덱스별로 유지되는 창. 양 끝에서는 범위를 벗어난 칸이 잘려 나갈 뿐, 반대쪽으로 넓어지지 않는다.
poolSize목록 중간에서 유지하는 인덱스의미
1{active}저사양 기기. 현재만
2{active, active+1}앞을 버리고 뒤를 택함
3{active-1, active, active+1}기본값
4{active-1, active, active+1, active+2}뒤가 하나 더

목록 양 끝에서는 범위를 벗어난 인덱스를 버리기만 하고 창을 안쪽으로 밀지 않습니다. 첫 페이지에서 {-1, 0, 1} 이 나오면 {0, 1} 로 줄어들 뿐, {0, 1, 2} 로 넓히지 않아요. 끝에는 미리 받아 둘 영상이 애초에 없으니, 반대쪽으로 넓히면 쓰지도 않을 인스턴스를 하나 더 만드는 셈입니다.

상한은 기기가 정한다

화면이 요청한 풀 크기는 상한이 아니라 희망값입니다. 실제 값은 기기 프로파일과 비교해서 작은 쪽으로 정해집니다.

private val poolSize: Int = requestedPoolSize.coerceAtMost(profile.poolSize)

// VideoDeviceProfile.forDevice()
val lowRam = am?.isLowRamDevice ?: false
val memoryClassMb = am?.memoryClass ?: Int.MAX_VALUE
return if (lowRam || memoryClassMb <= 128) LOW else NORMAL

프로파일은 풀 크기만 정하는 게 아니라 버퍼 예산과 화질 상한까지 함께 정합니다. 여기서 눈여겨볼 건 media3 기본값보다 낮춰 잡았다는 점이에요. DefaultLoadControl 의 기본 버퍼는 50초/50초/1초/2초인데(이 글의 media3 수치는 모두 1.10.1 기준입니다. 1.4.1 만 해도 뒤 두 값이 2.5초/5초였습니다)[2], 50초를 그대로 두면 창 안의 세 인스턴스가 각자 50초를 선행 적재합니다. 대역폭과 최악 버퍼 길이를 함께 줄이려고 20초로 낮춘 것입니다.

다만 정확히 해 둘 것이 있어요. 여기서 손댄 건 시간 축뿐입니다. media3 에서 실제 메모리 상한은 targetBufferBytes 인데 toLoadControl() 은 그걸 부르지 않아 기본값(C.LENGTH_UNSET, 트랙별 계산 폴백)으로 남아 있습니다. 시간을 줄이면 선행 적재량이 줄어 메모리 피크도 따라 낮아지지만, 바이트 상한 자체는 아직 조정하지 않았습니다. 실측 후 손볼 후보입니다.

화질 상한은 고정 숫자가 아니라 실제로 그릴 크기에서 계산합니다. 이게 renderSize 를 생성자 필수 인자로 올린 이유예요. 110 × 165 dp 카드에 1080p 트랙을 받아 놓고 축소해 그리는 건 대역폭과 디코딩 비용을 그냥 버리는 일입니다.

internal fun TrackSelectionParameters.withProfileCaps(
    profile: VideoDeviceProfile,
    baseWidthPx: Int,
    baseHeightPx: Int,
): TrackSelectionParameters {
    val maxWidth = (baseWidthPx * profile.videoSizeFraction).roundToInt()
        .coerceIn(1, profile.maxVideoLongSidePx)
    val maxHeight = (baseHeightPx * profile.videoSizeFraction).roundToInt()
        .coerceIn(1, profile.maxVideoLongSidePx)
    return buildUpon()
        .setMaxVideoSize(maxWidth, maxHeight)
        .setMaxVideoBitrate(profile.maxVideoBitrate)
        .build()
}

창 밖으로 나가면 stop() 까지

바인딩을 푸는 코드는 세 줄인데, 그 세 줄이 각각 다른 일을 합니다.

private fun unbind(videoIndex: Int) {
    bindings.remove(videoIndex)?.let {
        it.player.playWhenReady = false
        stateStore.onUnbound(it.player, videoIndex)
        it.player.stop()
    }
}

playWhenReady = false 만으로는 부족합니다. 일시정지된 플레이어는 여전히 미디어를 내려받고 디코더를 잡고 있어요. stop() 까지 해야 창 밖으로 밀린 플레이어가 로딩과 디코더 점유를 실제로 놓습니다. 그 사이에 있는 onUnbound 는 상태 저장소에서 그 슬롯의 기록을 지우는데, 이게 다음 절의 주제입니다.

인스턴스 자체는 버리지 않습니다. obtainIdlePlayer() 가 놀고 있는 인스턴스를 먼저 찾고, 없을 때만 새로 만들되 poolSize 에 도달하면 null 을 돌려줍니다. 재사용 쪽 계약은 탭 대상을 계속 바꿔도 플레이어는 하나만 만든다 가 직접 확인하고, 상한에 걸렸을 때의 동작은 poolSize 1 이면 창에 슬롯이 하나만 남는다 가 받습니다.

4. 상태는 플레이어에 매달지 않는다

인스턴스를 돌려 쓰기 시작하면 바로 따라오는 문제가 있습니다. 같은 플레이어가 어제는 A 영상을, 지금은 B 영상을 틀고 있다는 것. 그래서 상태를 플레이어에 매달면 안 됩니다. 스와이프 한 번을 끝까지 따라가 보면 이 설계가 왜 필요한지 보입니다.

스와이프 한 번의 경로
  • 1VerticalPager 의 settledPage 가 바뀐다. snapshotFlow 가 이를 잡아 먼저 로그용 콜백을 쏘고, 그 다음 controller.setActiveVideo(page) 를 호출한다
  • 2VideoPool 이 activeIndex 를 갱신하고, 바뀌었으면 userPaused 를 지우고 ticksHandler.onEntered() 로 진입 횟수를 올린다
  • 3keepIndices 로 새 창을 계산한다
  • 4창 밖 슬롯을 unbind 하고, 창 안의 빈 슬롯에 bind 한다. bind 는 stop() → setMediaItem() → prepare() 순서로 돌고, 상태 저장소에는 Buffering 으로 먼저 적어 둔다
  • 5활성이 아닌 슬롯은 재생 위치를 0으로 되돌리고 멈춘다. 활성 슬롯은 활성이 바뀐 경우에만 재생을 시작한다
  • 6플레이어 리스너가 onPlaybackStateChanged 등으로 응답하면 VideoStateStore.publish 가 그 플레이어가 들고 있는 슬롯을 찾아 상태를 갱신한다

5번의 "활성이 바뀐 경우에만" 이 은근히 중요합니다. 같은 인덱스로 setActiveVideo 가 다시 불릴 일이 꽤 있는데(목록이 갱신되거나 화면이 재구성될 때), 여기서 무조건 playWhenReady = true 로 덮으면 사용자가 탭해서 멈춰 둔 영상이 혼자 다시 재생됩니다.

상태 저장소의 비대칭

VideoStateStore 는 세 개의 맵을 들고 있는데, 키가 서로 다릅니다.

private val loaded = mutableMapOf<ExoPlayer, Slot>()
private val states = mutableStateMapOf<Int, VideoState>()
private val audioAvailability = mutableStateMapOf<String, Boolean>()

private data class Slot(val videoIndex: Int, val item: VideoItem)

loaded 는 플레이어를 키로 씁니다. 리스너 콜백은 플레이어 단위로 오니까, 그걸 슬롯으로 되짚으려면 이 방향이 필요해요. states 는 슬롯 번호가 키입니다. UI가 "3번 영상의 상태" 를 묻기 때문이죠. (이 글에서 "슬롯" 은 모두 영상 순번을 가리킵니다. 카드 번호라는 다른 좌표계는 7절에서 따로 등장합니다.) 그런데 audioAvailability 만 영상 ID 가 키입니다.

오디오 유무는 슬롯이 아니라 미디어의 성질이므로 영상 ID 로 기억한다.

이 차이가 만드는 결과는 이렇습니다. 오디오 트랙이 없는 영상을 봤다가 다른 영상으로 넘어갔다 돌아오면, 슬롯 번호도 플레이어 인스턴스도 달라질 수 있지만 "이 영상엔 소리가 없다" 는 사실은 그대로 남습니다. 덕분에 음소거 버튼을 다시 눌렀을 때 "소리가 없는 영상입니다" 안내를 곧바로 낼 수 있어요.

VideoHandle 은 좌표가 아니라 티켓이다

UI가 플레이어를 받아 가는 유일한 통로는 VideoHandle 입니다. 이름만 보면 인덱스를 감싼 것 같지만, 실제로는 네 가지를 함께 묶은 티켓입니다.

override fun playerFor(handle: VideoHandle): ExoPlayer? {
    return pool.bindingAt(handle.videoIndex)
        ?.takeIf { it.itemId == handle.itemId && it.generation == handle.generation }
        ?.player
}

인덱스로 현재 바인딩을 찾은 다음, 영상 ID와 세대 번호가 둘 다 맞아야 플레이어를 내줍니다. 세대는 바인딩이 새로 생길 때마다 증가하는 값이라(PageBinding(player, video.id, i, ++generation)), 같은 인덱스에 같은 영상이 다시 붙어도 이전 티켓은 무효가 됩니다. 여기에 owner 동일성까지 equals 에 포함돼 있어서, 컨트롤러가 통째로 교체된 경우의 낡은 참조도 걸러집니다.

이게 없으면 어떤 일이 생길까요. 스와이프 직후 아직 컴포지션이 정리되지 않은 이전 화면이 playerFor 를 호출해 지금 다른 영상을 틀고 있는 플레이어를 받아 갑니다. 그 화면이 표면을 붙이거나 정지를 호출하면, 사용자 눈에는 방금 넘어온 영상이 멈추거나 엉뚱한 자리에 뜹니다.

재생 위치는 틱으로 흘린다

진행률 표시와 로그는 둘 다 "지금 몇 초" 를 필요로 하는데, 이 값은 Compose 상태로 관찰할 수 없습니다. VideoTickHandler 가 200ms 주기로 흘려 주는 이유예요. 다만 이 틱은 위치만 담고 있지 않습니다.

data class VideoTick(
    val itemId: String,
    val positionMs: Long,
    val durationMs: Long,
    val entry: Int,   // 이 영상에 몇 번째로 진입했는가
    val lap: Int,     // 그 진입 안에서 몇 번째 반복인가
    val videoIndex: Int,
)

entry 는 활성이 바뀌거나(setActiveVideo) 처음부터 다시 재생할 때(replayActive) 올라가고, lap 은 자동 반복 전환(DISCONTINUITY_REASON_AUTO_TRANSITION)일 때만 올라갑니다. 이 두 숫자가 있어야 ShortformProgressTracker 가 "25% 지점 도달" 을 반복마다 한 번씩 정확히 셀 수 있어요. 숫자 없이 위치만 보면, 영상이 한 바퀴 돌아 다시 25%를 지날 때 이게 새 시청인지 같은 시청의 되감기인지 구분할 방법이 없습니다.

틱을 안 내는 조건도 명시적입니다. 활성 바인딩이 없거나, 라이브 스트림이거나, 길이를 아직 모르면(contentDuration <= 0) 아무것도 내지 않아요. 길이를 모르는 채로 틱을 내보내면 퍼센트 계산이 0으로 나누기가 됩니다.

5. 실패를 어떻게 분류했나

재생은 생각보다 자주 실패합니다. 네트워크가 끊기고, 서버가 5xx를 주고, 다른 앱이 카메라를 켜면서 코덱을 가져갑니다. 문제는 이 실패들이 사용자에게 같은 얼굴로 보이면 안 된다는 것입니다. 다시 눌러서 될 일이면 재시도 버튼을 줘야 하고, 몇 번을 눌러도 안 될 일이면 주지 말아야 해요.

private fun isRetryable(errorCode: Int, httpStatus: Int?): Boolean {
    if (httpStatus != null) {
        return httpStatus == HTTP_REQUEST_TIMEOUT ||   // 408
            httpStatus == HTTP_TOO_MANY_REQUESTS ||        // 429
            httpStatus >= HTTP_SERVER_ERROR_MIN           // 5xx
    }
    return errorCode == PlaybackException.ERROR_CODE_IO_NETWORK_CONNECTION_FAILED ||
        errorCode == PlaybackException.ERROR_CODE_IO_NETWORK_CONNECTION_TIMEOUT ||
        errorCode == PlaybackException.ERROR_CODE_DECODING_RESOURCES_RECLAIMED
}

HTTP 상태가 잡히면 그걸 우선합니다. 408(요청 시간초과), 429(요청 과다), 5xx는 서버 쪽 사정이라 잠시 후 다시 하면 될 수 있고, 403이나 404는 다시 눌러도 같은 답이 옵니다. HTTP 상태는 media3 예외 체인을 따라 내려가며 InvalidResponseCodeException 을 찾아 꺼냅니다.

디코더 계열에서 하나만 재시도 대상인 이유

흥미로운 건 디코더 쪽입니다. 디코더 관련 에러 코드가 여럿인데 단 하나만 재시도 대상입니다.

코드media3 원문 설명[3]판정
4006
RESOURCES_RECLAIMED		 Caused by higher priority task reclaiming resources needed for decoding. 재시도
4001
DECODER_INIT_FAILED		 Caused by a decoder initialization failure. 제외

표에 없는 4002 DECODER_QUERY_FAILED 와 4003 DECODING_FAILED 도 같은 이유로 제외입니다. 위 표는 전수가 아니라 판정이 갈리는 자리만 추린 것이에요.

4006은 원문이 "higher priority task 가 디코딩에 필요한 자원을 회수했다" 라고 명시합니다. 사유가 외부에 있고, 그 사유가 사라지면 그대로 다시 재생돼요. 다른 앱이 카메라를 켜거나 전화가 오면 생기는 일이니 재시도가 성공할 여지가 충분합니다.

반면 4001은 "디코더 초기화 실패" 라고만 말합니다. 인스턴스 상한을 넘어선 일시적 실패와, 그 포맷의 디코더가 기기에 아예 없는 영구적 실패가 같은 코드로 옵니다. 둘을 구분할 정보가 예외에 없습니다. 그래서 더 나쁜 쪽(영구 실패)을 기본으로 가정했어요. 일시적 실패를 영구로 오인하면 재시도 한 번을 잃지만, 반대로 두면 눌러도 성공할 수 없는 버튼을 계속 보여주게 되니까요. 배포 후 4001의 실제 분포를 보고 되돌릴 수 있는 결정입니다. 4004와 4005는 이름 자체가 "이 기기로는 안 된다" 라서 논의의 여지가 없고요.

실패는 덮이지 않는다

또 하나의 규칙은 상태 전이에 있습니다.

fun next(current: VideoState?, incoming: VideoState): VideoState {
    return if (current is VideoState.Failed && incoming !is VideoState.Failed) current else incoming
}

한 번 Failed 가 되면 새로운 Failed 로만 갱신되고, Idle 이나 Buffering 으로는 덮이지 않습니다. 이게 필요한 이유는 media3 의 콜백 순서에 있습니다. 공식 문서가 "When a failure occurs, this method will be called immediately before the playback state transitions to Player.STATE_IDLE" 라고 못 박고 있습니다.[7] 즉 onPlayerError 바로 뒤에 onPlaybackStateChanged(STATE_IDLE) 가 반드시 따라옵니다. sticky 처리가 없으면 에러 화면이 떴다가 곧바로 아무 일 없다는 듯 사라집니다.

이 절의 규칙들은 테스트 이름으로 그대로 남아 있습니다. 코덱 자원 회수는 일시적 사유이므로 재시도 대상이다, 디코더 초기화 실패는 재시도해도 같은 결과이므로 재시도 대상이 아니다, 실패 상태는 Buffering 전이에도 덮이지 않는다 처럼요. VideoStateMappingTest 한 파일에 22개가 들어 있습니다.

6. 소리는 한 화면만 낸다

영상이 세 지면에 생기면서 새로 생긴 문제가 있습니다. 라이브커머스가 PiP로 떠 있는 상태에서 숏폼에 들어가면 소리가 겹칩니다. 둘 다 자기 소리를 낼 권리가 있다고 믿으니까요.

해결은 점유자를 하나만 두는 것입니다. KurlyAudioManager 는 @Singleton 이고, 들고 있는 건 현재 점유자 하나뿐이에요.

fun claim(owner: AudioOwner) {
    audioOwner.value = owner
}

fun release(owner: AudioOwner) {
    audioOwner.compareAndSet(owner, null)
}

fun takenByOther(self: AudioOwnerType): Flow<Boolean> {
    return audioOwner.map { it != null && it.type != self }
}

release 가 단순 대입이 아니라 compareAndSet 인 게 핵심입니다. 화면 전환 순서를 생각해 보면 이유가 보여요. 사라지는 화면의 ON_PAUSE 가 먼저 오고, 새 화면이 claim 을 하고, 그 다음에야 사라진 화면의 onDispose 가 도착합니다. 단순 대입이면 새 화면이 방금 가져간 점유를 이전 화면이 지우고 갑니다.

해제 신호가 가장 늦게 도착해도 점유자는 바뀌지 않는다. 단순 대입이었다면 마지막 칸이 null 이 된다.

그리고 AudioOwner 는 종류만으로 식별하지 않습니다. AudioOwner(type, id = UUID.randomUUID().toString()) 처럼 화면 인스턴스마다 고유한 id 를 함께 듭니다. 같은 type 을 쓰는 화면이 둘 이상 살아 있을 수 있기 때문입니다. 홈에서 들어간 숏폼 위에 상품상세를 열고 거기서 또 숏폼을 열면, SHORTFORM 화면이 두 개 겹칩니다. 종류만으로 식별하면 뒤로가기 도중 사라지는 화면의 지연된 해제 신호가 이미 점유를 가져간 다른 숏폼의 점유까지 풀어 버립니다.

다만 takenByOther 는 다른 종류 가 점유했을 때만 true 를 냅니다. 같은 종류의 다른 인스턴스는 어차피 백그라운드라 소리를 내지 않거든요.

웹뷰 쪽은 한 번 더 밀어 넣어야 한다

숏폼 쪽 대응은 간단합니다. audioTakenByOther 가 true 가 되면 controller.setMuted(true) 를 부르면 끝이에요. 라이브커머스는 Grip 웹뷰라 사정이 다릅니다.

// LiveCommerceWebViewViewModel
private fun applyMute(occupied: Boolean) {
    if (mutedByOtherAudio == occupied) return
    mutedByOtherAudio = occupied
    if (occupied) mediaController.setMute(true)
}

fun reapplyMute() {
    if (!mutedByOtherAudio) return
    mediaController.setMute(true)
}

웹 플레이어의 재생 경로가 음소거 설정을 덮어쓰기 때문에, 재생 상태를 건드린 뒤에는 reapplyMute() 로 한 번 더 밀어 넣어야 합니다. 한 번 걸어 두면 유지되는 네이티브 플레이어와 다른 지점입니다.

점유 반납도 빼먹으면 안 됩니다. KurlyAudioManager 가 @Singleton 이라, 라이브커머스가 onCleared 에서 반납하지 않으면 화면이 사라진 뒤에도 점유자가 LIVE_COMMERCE 로 남습니다. 그러면 나중에 들어온 숏폼이 겹치는 소리가 하나도 없는데 강제 음소거됩니다.

7. 밟으면 아픈 것 넷

여기부터는 설계의 큰 줄기에서 벗어나 있지만, 밟으면 아픈 것들입니다.

가. Int 두 개가 같은 표면에 있으면 반드시 섞인다

영상이 드문드문 섞인 지면을 생각해 봅시다. 카드 5개 중 1번과 4번만 영상이면, 카드 번호와 영상 순번이라는 두 좌표계가 생깁니다. 4번 카드의 영상 순번은 1이에요. 둘 다 Int 라서, 한 인터페이스에 섞여 있으면 호출자가 조용히 엉뚱한 영상을 붙입니다. 컴파일러는 아무 말도 하지 않고요.

카드 4번의 영상 순번은 1이다. 두 줄의 숫자가 어긋나는데 타입은 둘 다 Int 다.

SparseVideoController 는 이 문제를 위임을 노출하지 않는 것으로 풉니다. VideoController 를 상속하거나 by delegate 로 펼치지 않고, 카드 번호만 받는 함수를 새로 정의해요. 영상 순번이 필요한 호출자는 videoIndexAt(cardIndex) 로 명시적으로 변환한 다음 videoController 프로퍼티를 씁니다. 변환을 건너뛸 수 없게 만든 것입니다.

아직 호출부가 없습니다

SparseVideoController 와 SparseVideoPlaylist 는 구현과 테스트(SparseVideoControllerTest, SparseVideoControllerPlaybackTest, SparseVideoPlaylistTest)까지 들어와 있지만, 이번 변경의 프로덕션 코드에서 부르는 곳은 아직 한 군데도 없습니다. 영상과 이미지가 섞이는 지면을 염두에 두고 먼저 설계해 둔 API 이고, 그 지면이 실제로 붙을 때 계약이 맞는지 확인하게 됩니다.

나. 가드를 호출자에게 맡기지 않는다

SparseVideoController.setSettledCard 는 같은 카드로 다시 불리면 아무것도 하지 않습니다. 이 가드가 함수 안에 있는 게 중요해요.

fun setSettledCard(cardIndex: Int) {
    val current = playlist()
    if (settledCard == cardIndex && settledPlaylist == current) return
    settledCard = cardIndex
    settledPlaylist = current
    delegate.preload(current.videoIndicesNear(cardIndex, MAX_CARD_DISTANCE))
}

preload 는 재생을 멈추고 위치를 0으로 되돌립니다. 가드를 호출자에게 맡기면, 목록이 갱신되거나 같은 카드에 재정착하는 것만으로 재생 중이던 영상이 처음으로 돌아갑니다. 호출자가 빠뜨릴 수 있는 가드는 호출자에게 주지 않는다는 원칙인데, 이 저장소에서는 NavBackStack 을 pop 하는 함수에도 같은 규칙이 적용돼 있죠.

반대로 목록이 바뀌었으면 같은 카드라도 창을 다시 잡습니다. setItems 가 내용이 달라진 슬롯의 바인딩을 해제하니까, 여기서까지 막으면 그 카드가 빈 채로 남거든요. 그래서 SparseVideoPlaylist 는 equals 를 직접 구현해 "카드와 영상 매핑이 같고 영상 내용도 같으면 같은 목록" 이라는 계약을 명시합니다.

다. 컨트롤러는 IO에서 만들고, 플레이어는 메인에서 만든다

media3 문서는 분명히 말합니다. "ExoPlayer instances must be accessed from a single application thread."[4] 그런데 컨트롤러 생성 코드는 이렇게 생겼습니다.

controller = withContext(Dispatchers.IO) {
    DefaultVideoController(context, poolSize, renderSize, loop)
}.apply { setItems(latestItems) }

모순처럼 보이지만 아닙니다. DefaultVideoController 생성자는 ExoPlayer 를 만들지 않아요. 만드는 건 VideoDataSourceFactory 이고, 이게 SimpleCache 를 초기화하면서 디스크 I/O를 합니다(캐시 디렉터리 생성과 인덱스 데이터베이스 열기). 200MB LRU 캐시를 메인 스레드에서 여는 걸 피하려고 IO로 보낸 것입니다.

실제 ExoPlayer 인스턴스는 bindMissingInWindow 안의 createInstance() 에서 처음 만들어지고, 그 경로는 setActiveVideo 와 preload 를 타고 들어옵니다. 둘 다 @MainThread 계약 위에 있습니다. VideoController 인터페이스에는 @MainThread 가 붙어 있고, 호출부는 컴포지션 본문(KurlyVideo 의 itemAt, stateAt, handleAt), LaunchedEffect(setActiveVideo), LifecycleEventObserver(pause, resume), 클릭 콜백(toggleMuted, retry)으로 흩어져 있습니다. 공통점은 전부 메인 스레드로 디스패치되는 자리라는 것입니다.

다만 @MainThread 는 린트 힌트일 뿐 런타임이 강제하지 않습니다. 호출부가 늘어날 때 이 계약을 지켜 주는 건 어노테이션이 아니라 "컨트롤러를 Composable 바깥으로 들고 나가지 않는다" 는 사용 규칙이에요. rememberVideoController 가 컨트롤러를 오직 컴포지션 안에서만 만들고 DisposableEffect 로 같이 버리는 것도 그 규칙을 코드로 굳힌 것입니다.

라. 헤더 주입은 ResolvingDataSource 로

컬리 미디어 CDN은 정적 Referer 헤더를 요구합니다. 문제는 이 헤더를 미디어 요청에만 붙여야 한다는 것인데, MediaItem 마다 헤더를 지정하는 방식은 호출부가 늘어날수록 빠뜨리기 쉽습니다. media3 가 공식 문서에서 제시하는 관용구가 정확히 이 상황을 위한 것이었어요.[5]

internal object KVLMediaRefererResolver : ResolvingDataSource.Resolver {

    override fun resolveDataSpec(dataSpec: DataSpec): DataSpec {
        val host = dataSpec.uri.host ?: return dataSpec
        if (!KVLMediaHost.matches(host)) return dataSpec
        return dataSpec.withAdditionalHeaders(
            mapOf(KVLMediaRefererHeader.KEY to KVLMediaRefererHeader.VALUE)
        )
    }
}

데이터소스 층에 한 번 꽂아 두면 모든 미디어 요청이 이 경로를 지납니다. 호스트 판정은 대소문자를 정규화한 뒤에 합니다. 호스트명은 대소문자를 구분하지 않으니까 그렇습니다.

8. 한계와 다음

media3 에는 이미 프리로드 매니저가 있다

글을 마무리하면서 확인한 사실을 그대로 적습니다. media3 에는 DefaultPreloadManager 가 있고, 공식 문서는 그 첫 문단에서 "an app might show a carousel of short videos" 를 정면 유스케이스로 듭니다.[6] 이 구현을 시작할 때 저희는 그 존재를 검토하지 않았습니다.

그래서 "검토 후 배제했다" 고 쓰지 않겠습니다. 대신 지금 문서를 읽고 확인한 것만 적으면, 둘은 겹치지만 같은 문제를 풀지는 않습니다. 문서가 앱의 책임으로 명시하는 항목 중 첫 번째가 이것입니다.

Create the app's ExoPlayer objects by using the same DefaultPreloadManager.Builder object you use to create the preload manager.

즉 DefaultPreloadManager 는 어떤 항목을 얼마나 미리 받을지를 우선순위에 따라 관리하고, MediaSource 를 넘겨줍니다. 인스턴스를 몇 개 둘지, 어떤 슬롯에 붙일지, 그 슬롯의 상태와 실패를 어떻게 귀속할지는 여전히 앱의 몫이에요. 이 글이 다룬 VideoPool 의 일이 대부분 후자입니다. 대체재라기보다 아래위로 붙는 보완재에 가깝고, 적어도 keepIndices 가 창을 정하는 로직은 겹칩니다. 우선순위 랭킹과 적재량 제어까지 겹치는지는 문서만 읽고 단정할 수 없고, 실제로 붙여 봐야 압니다.

결정DefaultPreloadManager이 글의 VideoPool
어떤 항목을 미리 받나우선순위 랭킹keepIndices (겹침)
얼마나 받나적재 상태 단계창 크기로 간접
인스턴스를 몇 개 두나앱 책임poolSize + 기기 프로파일
슬롯과 영상의 귀속앱 책임PageBinding + generation
실패 귀속과 재시도 판정앱 책임VideoStateStore

다만 겹치는 그 부분을 라이브러리에 넘길 수 있다면 VideoPool 은 더 작아집니다. 다음 개선 후보로 올려 두었습니다. DefaultPreloadManager 가 @UnstableApi 라는 점은 결정적인 걸림돌은 아닙니다. VideoPool 도 이미 @UnstableApi 표면 위에 서 있거든요.

아직 사용자에게 나가지 않았다

이 변경은 QA 진행 중이고 아직 배포되지 않았습니다. 그래서 이 글에는 첫 프레임 시간이나 버퍼링 비율 같은 운영 수치가 없습니다. 기획에 적힌 UX 가드레일(첫 프레임 p75 1.5초, 버퍼링 3% 미만, 스크롤 FPS p75 45 이상)은 지켜야 할 목표치이지 달성한 결과가 아닙니다. 특히 VideoDeviceProfile 의 임계값(memoryClass <= 128)과 LOW 프로파일 값은 실기기 측정 없이 정한 보수적 추정이라, 배포 후 실측으로 다시 조정할 자리입니다.

가져갈 것

1. 인스턴스를 돌려 쓰는 순간 상태의 주인이 바뀝니다. 플레이어에 상태를 매달면 같은 인스턴스가 다른 영상을 틀 때 조용히 어긋납니다. 슬롯 번호, 콘텐츠 ID, 세대 번호 중 무엇을 키로 쓸지는 "그 사실이 무엇에 속하는가" 로 정합니다. 오디오 유무는 미디어의 성질이니 영상 ID, 재생 상태는 화면의 성질이니 슬롯 번호입니다.

2. 재사용되는 자원의 참조에는 유효기간을 붙입니다. 인덱스만으로 플레이어를 내주면 낡은 참조를 막을 수 없습니다. 세대 번호 하나를 추가하는 비용은 Long 필드 하나인데, 막아 주는 건 재현하기 매우 어려운 부류의 버그입니다.

3. 실패는 재시도 가능 여부로 나눕니다. 그리고 그 판정의 근거는 라이브러리 문서의 원문이어야 합니다. "디코더 에러니까 재시도" 같은 뭉뚱그린 분류는 성공할 수 없는 버튼을 사용자에게 보여줍니다.

4. 모듈 경계는 의존성 선언에 드러납니다. :video 가 :domain 을 의존하지 않는다는 한 줄의 부재가, 이 모듈이 숏폼 전용이 아니라는 사실을 문서보다 강하게 보장합니다.

영상이 붙을 지면이 앞으로 더 생긴다면, 그 화면이 새로 작성할 것은 "무엇을 보여줄지" 뿐이어야 합니다. 몇 개를 살려 둘지는 이미 정해져 있어야 하고요. 이 글의 설계가 겨눈 지점이 거기입니다.
