Android 12 스플래시 인계 레이스 · 구간 실측

window 는 충분히 넓었다

SM-G973N에서 같은 크래시 경로를 조건별로 측정했다. 부하를 걸면 레이스 창이 프로덕션 급인 1,282ms까지 벌어지는데도 크래시하지 않는다. 막고 있는 것은 폭이 아니라 순서다. 크래시는 붉은 onDestroy 막대가 청록 window 막대보다 먼저 끝날 때만 일어난다.

읽는 법

모든 시각은 AppStarterActivity.onResume을 0으로 맞췄다. 네 막대의 정의는 이렇다.

app boot
앱구간. onResume에서 앱의 첫 HTTP 요청이 인터셉터에 닿기까지다. Hilt 그래프 구성과 토큰 로드, OkHttp 클라이언트 준비가 여기 들어간다. 이 막대의 끝이 곧 점검 판정 시각이다. 앱이 그보다 이른 시각에 점검을 알 방법은 없다. 네트워크 왕복을 0으로 만들어도 이 길이는 줄지 않는다.
system
시스템구간. 앱의 첫 preDraw에서 ATTACH_TO가 도착하기까지다. 그 사이에 requestCopySplashScreen()이 shell에 복사를 요청하고 shell이 스플래시 비트맵을 돌려준다. system_server와 SystemUI의 왕복이고 앱 코드가 아니다.
window
레이스 창. ATTACH_TO 도착에서 HANDOVER_TO 도착까지다. 두 번째 디스패치가 이 창의 끝에 온다. 액티비티 제거가 이 안에서 끝나면 도착한 HANDOVER_TO가 죽은 레코드를 만나 크래시한다.
onDestroy
액티비티 제거. 점검 판정에서 AppStarterActivity의 onDestroy 완료까지다. 공지 웹뷰를 CLEAR_TASK로 띄우고 그 웹뷰가 뜨는 동안 이전 액티비티가 제거되므로 약 1초가 걸린다. 이 1초가 창보다 짧아야 한다.

세로 선 두 개는 ATTACH와 판정이다. 판정이 ATTACH보다 왼쪽에 서면 공지 웹뷰가 전송 도중에 로딩되며 메인 스레드를 점유해 window를 스스로 벌린다. 오른쪽에 서면 벌어질 일이 없다.

4. 왜 부하가 듣지 않는가

두 구간의 비율을 보면 답이 나온다. 크래시 조건을 비율로 다시 쓰면 이렇다.

앱구간 ÷ 시스템구간 < 1 + 80ms ÷ 시스템구간  즉 기준선에서는 1.10 미만, 부하에서는 1.02 미만이어야 한다.

부하를 5배로 걸어도 비율은 1.44와 1.63으로 관측 구간에 그대로 남는다. 균일한 부하는 분자와 분모를 같이 키우므로 비율을 바꾸지 못한다. 첫 프레임을 300ms 보류한 실험이 실패한 것도 같은 이유다. 앱 메인 스레드를 늦추면 ATTACH와 첫 요청이 함께 밀린다.

5. 프로덕션은 어디에 있었는가

Crashlytics breadcrumb으로 역산하면 프로덕션의 앱구간은 약 1,152ms다. 우리 기준선 1,150ms와 사실상 같다. 그러면 위 부등식에서 프로덕션의 시스템구간이 1,072ms 이상이어야 국면 A에 들어간다.

프로덕션 행은 측정값이 아니다. 직접 관측된 것은 breadcrumb 델타 하나뿐이고, 나머지는 크래시가 실제로 발생했다는 사실과 위 부등식에서 역산한 하한과 상한이다. 프로덕션의 ATTACH 시각은 관측할 수 없으므로 판정과 ATTACH 의 간격도 부호만 알 수 있다.

프로덕션은 앱은 우리와 같은 속도였고 시스템 쪽만 30% 정도 느렸다. 우리 부하 시험은 5배를 균일하게 걸었으니 조준이 틀렸다. 필요한 것은 시스템구간만 1.3배 늘리는 것이었다.

측정 기기 SM-G973N (Android 12, SDK 31, One UI 4.1, SP1A.210812.016.G973NKSU7HWD3), betaDebug 빌드, 실제 런처 아이콘 탭. 시각 기준은 AppStarterActivity.onResume = 0.

판정은 첫 HTTP 요청 진입보다 1에서 15ms 늦으므로 같은 값으로 취급했다. 부하 회차의 onDestroy는 15초 캡처 창을 넘어 미포착이라 onDestroy 막대를 점선으로 표시했다. 부하 3회차는 ATTACH 미포착으로 제외했다. 주입 재현 회차의 window는 인계가 도달하지 않아 점선이다.
