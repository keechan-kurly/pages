세 가지 설계 결정

컬리 안드로이드 앱의 네비게이션 시스템을 다시 설계했다. 핵심 결정은 세 가지다.

  • Delegator 42개를 sealed Destination 모델로  파편화된 진입 로직을 타입 안전한 단일 모델로 통합
  • 호출을 두 갈래로 — 내부 진입과 외부 URL  DestinationNavigator(내부)와 UriNavigator(외부)가 같은 IntentGenerator에서 합류
  • 단일 :navigation 모듈을 네 개로  api·impl·di 분할과 함께 IntentGenerator·Resolver를 모듈 경계에 맞게 재배치

이 결정들의 결과가 409개 파일, +6,076 / −3,864이다.[1] 이런 규모가 한 PR에 들어가면 보통 머지가 영원히 지연되거나, 머지된 다음 한동안 회귀가 쏟아진다. 그래서 작업을 여섯 단계로 분해했다. 각 단계는 다음 단계의 전제 조건만 만족시키고 끝낸다. 단계의 흐름이 곧 PR 안의 커밋 순서가 됐다.

이 글은 두 축을 다룬다. (1) 위의 세 설계 결정이 코드에서 어떤 모습으로 나타나는가, (2) 그 결정을 한 PR에 안전하게 담은 여섯 단계의 흐름.

리팩토링 전 · Delegator 42개와 :app에 모인 모든 것

기존 네비게이션은 Delegator 패턴 위에 4년간 쌓여 있었다. 화면 하나를 추가할 때마다 인터페이스 1개, 구현체 1개, Hilt 바인딩 1개가 따라붙었고, 딥링크까지 필요하면 NavDelegator가 추가로 늘어 파일이 다섯 개까지 늘었다.

// :features — 인터페이스 정의
interface HomeDelegator {
    fun navigateToHome(context: Context, site: String?)
}

// :app — 구현체
class HomeDelegatorImpl @Inject constructor(
    private val homeIntentGenerator: HomeIntentGenerator,
) : HomeDelegator {
    override fun navigateToHome(context: Context, site: String?) {
        val intent = homeIntentGenerator.generateIntent(context, site)
        context.startActivity(intent)
    }
}

호출부는 두 가지 패턴이 공존했다. Navigator 객체의 sub-delegator를 거치거나, Delegator를 직접 호출하거나.

// NavDelegator 경유
navigator.home.startMainActivity(context)
navigator.product.startProductDetailActivity(context, productNo)

// Delegator 직접 호출
bannerDelegator.handleUrl(context, url)
dialogDelegator.alert(fragmentManager, title, buttonText)

이 구조의 문제는 세 가지였다.

진입 로직의 파편화. 상품 상세 화면 하나를 호출하는 코드가 ProductNavDelegator, BannerDelegator, HomeDelegator, CategoryDelegator에 각각 존재했다. 파라미터 전달 방식이 Delegator마다 달랐다.

구현체의 :app 집중. 36개 Delegator 구현체와 43개 IntentGenerator가 모두 :app에 있었다. :features:product가 상품 상세 화면을 띄우려면 인터페이스를 거쳐 결국 :app의 구현체에 닿아야 했다. 멀티모듈 의존 그래프가 깊었다.

딥링크 일관성 부재. 외부 URL 파싱 로직이 각 NavDelegator에 산재했다. kurly://product?no=123을 처리하는 코드와 kurly://home?site=market을 처리하는 코드가 다른 패턴을 사용했다.

목적지 · 어디로 가려 했는가

리팩토링이 끝났을 때의 모습을 먼저 보여두자. 각 단계는 이 그림을 향해 한 발씩 나아간다.

리팩토링 후 모듈 구조

:navigation:api  인터페이스만 — KurlyNavigator, Destination, DeepLinkSpec, ScreenResolver, OverlayResolver

:navigation:impl  구현체 — KurlyNavigatorImpl, DestinationNavigator, UriNavigator, 61개 Resolver, Hilt 모듈

:navigation:di  DI 진입점 모듈

:features:*  56개 IntentGenerator가 각자의 기능 모듈로 분산

:link  LoginRedirectProvider, KurlyUrlChecker 등 의존성 역전 인터페이스 + DeepLinkHost/Path/QueryParam 상수 체계

호출부에서 보면 모든 화면 전환이 두 패턴으로 수렴한다.

navigator.navigate(context, Destination.Screen.ProductDetail(productNo = 123L))
navigator.show(fragmentManager, Destination.Overlay.Alert(title, btn))

호출부는 어떤 Delegator의 어떤 메서드를 호출해야 하는지 알 필요가 없다. navigate와 show 두 가지만 안다.

이 그림으로 가는 길은 단번에 그어지지 않았다. 다음 여섯 단계를 거쳤다.

STAGE 1새 모듈과 인터페이스의 자리부터 만들기

가장 먼저 한 일은 새 모듈의 빈 자리를 만드는 것이었다. :navigation:api, :navigation:impl, :navigation:di 세 모듈을 스캐폴딩하고, settings.gradle.kts에 등록했다. 이 시점에서 코드는 한 줄도 옮기지 않았다. 빈 모듈만 만들어 두었다.

그다음 핵심 인터페이스 세 개를 :navigation:api에 정의했다.

// :navigation:api
interface KurlyNavigator {
    fun navigate(context: Context, destination: Destination.Screen)
    fun show(fragmentManager: FragmentManager, destination: Destination.Overlay)
    // ...
}

interface ScreenResolver<T : Destination.Screen> {
    fun resolve(context: Context, destination: T): Intent
}

interface DeepLinkSpec<T : Destination> {
    fun toUri(destination: T): Uri
}

이 단계의 목적은 "다음 단계가 의존할 수 있는 표면"을 만드는 것이다. 기능 모듈이 새 KurlyNavigator를 의존하려면 그 인터페이스가 어딘가에 존재해야 한다. 구현체가 없어도 인터페이스만 있으면 컴파일은 통과한다.

이 단계가 끝나면 코드베이스의 동작은 0% 변했다. 그러나 다음 단계의 모든 변화가 의지할 수 있는 자리가 만들어졌다.

STAGE 2Destination 모델과 Resolver 위임 패턴

두 번째 단계에서는 Destination sealed interface를 채우고, 각 화면마다 Resolver를 만들어 기존 IntentGenerator에 위임했다.

sealed interface Destination {
    sealed interface Screen : Destination {
        data class ProductDetail(val productNo: Long) : Screen
        data object Cart : Screen
        data class Home(val site: String? = null) : Screen
        // ...
    }
    sealed interface Overlay : Destination {
        data class Alert(val title: String, val buttonText: String) : Overlay
    }
}

파라미터가 있는 화면은 data class, 없는 화면은 data object로 구분했다. sealed interface의 when은 모든 화면을 처리했는지 컴파일러가 검증한다.[2]

Resolver는 기존 IntentGenerator를 그대로 재활용하는 위임 어댑터다. Intent 생성 로직은 건드리지 않았다.

class ProductDetailResolver @Inject constructor(
    private val intentGenerator: ProductIntentGenerator,
) : ScreenResolver<Destination.Screen.ProductDetail> {
    override fun resolve(
        context: Context,
        destination: Destination.Screen.ProductDetail,
    ): Intent {
        val uri = Destination.Screen.ProductDetail.toUri(destination)
        return intentGenerator.generateIntent(context, uri)
    }
}

각 화면의 Destination이 toUri()로 자신을 URI로 직렬화하면, Resolver가 그 URI를 기존 IntentGenerator에 넘긴다. IntentGenerator는 이미 외부 딥링크를 처리하던 코드이므로, 내부 진입도 같은 길을 거치게 된다.

Hilt의 @IntoMap 멀티바인딩으로 Resolver를 등록하면 DestinationNavigator가 Destination의 KClass를 키로 적합한 Resolver를 찾는다.

이 단계가 끝나면 새 시스템이 동작은 하지만, 누구도 호출하지 않는다. 기존 Delegator가 그대로 살아 있어 코드베이스의 모든 호출이 옛 길을 탄다. 다음 단계가 호출부를 옮긴다.

STAGE 3Delegator 42개 점진 제거

호출부 마이그레이션은 위험도가 가장 높은 단계다. 한 번에 모두 옮기면 변경 범위가 너무 넓어 PR 리뷰가 불가능해진다. 그래서 세 갈래로 나눴다.

Delegator 제거 순서 — 의존 루트부터 안으로

3-A. 의존 루트 차단  :navigation 모듈의 NavDelegator 5개와 Navigator 객체를 먼저 제거. 다른 모듈이 이 인터페이스에 의존하지 못하도록 루트부터 끊는다.

3-B. 저사용 Delegator  호출 지점이 1-2곳인 InquiryComposeDelegator, PickListDelegator 등. 리스크가 낮은 것부터.

3-C. 고사용 Delegator  BannerDelegator, HomeDelegator, BrandDelegator, CategoryDelegator, OrderResultDelegator. 변경 범위가 넓어 PR을 분리해 격리했다.

호출부 변환은 일관된 패턴을 따른다.

Before

navigator.cart.startCartActivity(ctx)

bannerDelegator.handleUrl(ctx, url)

STAGE 4KurlyNavigator를 얇은 라우터로 분리

Delegator를 모두 걷어내고 나니 KurlyNavigatorImpl이 너무 많은 책임을 안고 있다는 게 보였다.

한 클래스가 두 가지 다른 진입을 처리하고 있었다. 코드가 직접 Destination을 구성해서 들어오는 내부 진입, 그리고 외부 URL/URI/Route가 들어오는 외부 진입이다. 두 흐름은 검증 단계도 다르고, 실패 처리 방식도 다르다.

내부 진입은 컴파일 타임에 타입 검증을 받고 들어온다. Destination.Screen.ProductDetail(productNo = 123L)이 만들어진 시점에 이미 형식이 맞다. 외부 진입은 URL 파싱·로그인 정책·화이트리스트 검증·fallback 처리가 필요하다. 이건 :link 모듈의 LinkParser가 이미 잘하고 있던 영역이다.

4-A. 책임 둘로 가르기

KurlyNavigatorImpl을 얇은 라우터로 축소하고, 두 책임을 별도 클래스로 옮겼다.

class KurlyNavigatorImpl @Inject constructor(
    private val destinationNavigator: DestinationNavigator,
    private val uriNavigator: UriNavigator,
    private val uriGenerator: UriGenerator,
) : KurlyNavigator {

    // 내부 진입 — 코드가 Destination 을 직접 구성
    override fun navigate(context: Context, destination: Destination.Screen) {
        destinationNavigator.navigate(context, destination)
    }

    // 외부 진입 — URL/URI/Route
    override fun navigate(
        context: Context, url: String,
        fallback: FallbackAction, intentAction: IntentAction?,
    ): Boolean = uriNavigator.navigate(context, url, fallback, intentAction)

    override fun navigate(
        context: Context, route: Route,
        fallback: FallbackAction, intentAction: IntentAction?,
    ): Boolean {
        val uri = uriGenerator.bind(route)
        return uriNavigator.navigate(context, uri, fallback, intentAction)
    }
    // ... show(Overlay), navigate(Uri), isHandledDeepLink
}

DestinationNavigator는 Resolver 맵에서 적합한 Resolver를 찾아 Intent를 생성하고 액티비티를 시작한다. UriNavigator는 LinkParser에 위임해 URL을 해석하고 결과에 따라 Intent를 띄우거나 fallback을 동작시킨다. 둘은 서로를 모른다.

4-B. DeepLinkSpec은 toUri만 — 한 방향이면 충분한 이유

책임을 둘로 가르면 DeepLinkSpec의 형태가 자연스럽게 결정된다. 외부 URL은 UriNavigator가 LinkParser를 거쳐 적합한 Intent로 직접 변환한다 — 중간에 Destination을 거치지 않는다. 그러므로 DeepLinkSpec이 URL을 파싱해 Destination으로 복원하는 함수를 가질 필요가 없다.

// :navigation:api
interface DeepLinkSpec<T : Destination> {
    fun toUri(destination: T): Uri
}

toUri가 인터페이스에 남은 이유는 반대 방향의 수요 때문이다. 내부 코드가 외부에 노출할 URI를 만들어야 하는 경로가 있다 — 푸시 알림 트레이에 표시할 딥링크, 위젯에서 앱으로 들어오는 URL, 라우팅 테스트에 쓰는 URI 등.

Destination → URI는 매번 같은 규칙으로 변환되어야 한다. 각 화면의 DeepLinkSpec.toUri가 그 규칙을 한 곳에서 정의한다.

같은 분리 논리에 따라 별도의 URL→Destination 매핑 객체도 필요 없다. 외부 URL이 들어오면 UriNavigator가 LinkParser를 거쳐 적합한 IntentGenerator에 도달한다. DestinationNavigator는 코드가 직접 구성한 Destination만 처리하므로 URL을 해석할 일이 없다.

내부 진입과 외부 진입은 같은 파이프라인에 묶이면 한쪽이 다른 쪽의 정책을 떠안는다. DestinationNavigator는 타입 검증을 받은 내부 호출만, UriNavigator는 검증이 필요한 외부 URL만 처리한다.

STAGE 5모듈 재배치와 의존성 역전 인터페이스

인터페이스와 구현체의 자리는 모두 잡혔다. 그러나 36개 Resolver와 43개 IntentGenerator는 여전히 :app에 있었다. 멀티모듈 의존 그래프를 단축하려면 이들을 더 깊은 모듈로 옮겨야 했다.

5-A. IntentGenerator를 :features:*로 분산

43개 IntentGenerator를 각자 책임지는 기능 모듈로 옮겼다. ProductDetailIntentGenerator는 :features:product로, CategoryIntentGenerator는 :features:category로. :navigation:impl의 Resolver는 각 기능 모듈에 의존하면서 IntentGenerator를 주입받는다.

5-B. Resolver를 :navigation:impl로 모으기

41개 Resolver를 :app에서 :navigation:impl로 옮겼다. DestinationModule, NavigatorBindingModule도 함께 이동. :app은 더 이상 Resolver를 알 필요가 없다.

5-C. 의존성 역전 인터페이스 추출

이동 과정에서 의존 주기가 닫히는 자리가 발견됐다. LoginIntentGenerator는 로그인 후 돌아갈 곳을 정하기 위해 LoginRedirectProvider를 호출했다. 그런데 LoginRedirectProvider의 구현체는 :app에 있었다. LoginIntentGenerator를 :features:login으로 옮기면 :features:login이 :app을 의존해야 한다.

인터페이스를 추출해 :link 모듈로 올렸다. :link는 모든 기능 모듈이 의존하는 하위 모듈이다.

// :link — 인터페이스
interface LoginRedirectProvider {
    fun getRedirectUri(context: Context): Uri?
}

// :features:login — 구현체
class LoginRedirectProviderImpl @Inject constructor(/* ... */) : LoginRedirectProvider

같은 패턴을 두 군데 더 적용했다. :features 코드가 메인 화면 전환을 호출해야 하는데 MainActivity는 :app에 있어, MainActivityNavigator 인터페이스를 :features:core로 올렸다. URL이 컬리 도메인인지 검증하는 로직은 KurlyUrlChecker 인터페이스로 추출해 :link에 두었다.

5-D. KSP의 멀티모듈 처리

컬리 앱은 딥링크 컨버터를 KSP로 생성한다. @DeepLink 어노테이션을 붙인 클래스를 프로세서가 스캔해 DeepLinkConverter 구현체와 Hilt @IntoSet 바인딩을 자동 등록한다.

@DeepLink(
    title = "상품 상세",
    links = [DeepLink.Example("상품 상세 진입", "kurly://product?no=123")],
)
class ProductDetailIntentGenerator @Inject constructor(/* ... */) {
    // KSP 가 컨버터와 @IntoSet 바인딩을 자동 생성
}

이전에는 모든 @DeepLink 대상이 :app 한 모듈에 모여 있었다. KSP 프로세서가 한 모듈을 스캔해 한 번에 컨버터를 생성하면 됐다.

43개를 :features:*로 흩어놓자, 프로세서가 모듈마다 따로 동작했다. 자동 생성된 DeepLinkInjector들이 같은 이름으로 충돌하고, @IntoSet 바인딩은 모듈 경계를 넘지 못했다.

해결은 KSP 옵션과 가시성 변경의 조합이었다. KSP moduleId 옵션으로 생성 클래스 이름에 모듈 식별자를 붙여 충돌을 회피하고, 생성 클래스를 public으로 바꿔 다른 모듈에서 발견되게 했다. :features:brand, :features:category, :features:dynamiclist, :features:recipe 등에 KSP 설정을 추가했다.

"파일을 옮긴다"는 한 줄 결정이 어노테이션 프로세서의 생성 규칙과 Hilt 멀티바인딩의 가시성 정책을 동시에 건드리는 작업으로 번졌다.

STAGE 6매직 스트링 일원화와 Resolver 표준 패턴

마지막 단계는 정제다. 모듈이 갈라지자 한 쌍으로 작동해야 할 문자열들이 서로 다른 모듈에 분산됐다. 위험을 그대로 둘 수 없었다.

6-A. 매직 스트링 상수 체계 도입

Destination.ProductDetail.toUri()는 "product" 호스트에 "no" 쿼리를 붙여 URI를 만든다. ProductDetailIntentGenerator는 받은 URI에서 "no" 쿼리를 꺼낸다. 같은 문자열이 두 모듈에 하드코딩되어 있으면 한쪽이 바뀌었을 때 다른 쪽이 모른다.

세 단계의 상수 체계를 도입했다.

// :link/.../DeepLinkQueryParam.kt
object DeepLinkQueryParam {
    const val SITE = "site"

    object ProductDetail {
        const val NO = "no"
        const val REFERRER = "referrer"
        const val DEAL_NO = "dealNo"
        const val JOIN_ORDER_CODE = "joinCode"
    }
    // 22 개 nested object
}

DeepLinkHost(호스트 이름), DeepLinkPath(경로 세그먼트), DeepLinkQueryParam(쿼리 키). 세 개의 nested object 체계가 두 모듈을 가로지르는 모든 매직 스트링을 한 자리로 모았다.

6-B. 상수 정렬이 끄집어낸 키 일치 검증

매직 스트링을 상수로 옮기는 작업은 단순한 리팩토링으로 보였다. 그러나 정렬 과정에서 Destination.toUri()가 만든 URI를 IntentGenerator가 해석하지 못하는 케이스가 세 건 발견됐다.

검출 유형

쿼리 키 이름 불일치  toUri가 만드는 쿼리 키와 IntentGenerator가 읽는 키가 다른 케이스 (예: orderNo 작성 vs no 기대)

쿼리 vs path 위치 불일치  식별자를 한쪽은 쿼리로 넣고 다른 쪽은 path segment에서 읽는 케이스 (예: ?claimId=X vs /X)

path 세그먼트 이름 불일치  같은 의미의 path가 한쪽은 inquiry, 다른 쪽은 onetoone_inquiry 같은 식으로 달랐던 케이스

상수화 이전에는 같은 의미의 매직 스트링이 두 자리에 따로 적혀 있어 정적 분석에 잡히지 않는다. 같은 상수를 참조하도록 정렬하면 차이가 비로소 드러난다 — 같은 상수를 못 쓰는 자리가 곧 차이의 자리다.

키 정렬을 마치고 회귀를 막기 위한 검증 테스트를 추가했다. Destination.toUri()가 만든 URI가 IntentGenerator의 @DeepLink 규격과 일치하는지 화면 단위로 확인한다.

@Test
fun `OrderDetail toUri matches IntentGenerator contract`() {
    val uri = Destination.Screen.OrderDetail.toUri(
        Destination.Screen.OrderDetail(orderNo = "O123")
    )
    // @DeepLink 규격: kurly://order?no=...
    assertThat(uri.getQueryParameter(DeepLinkQueryParam.Order.NO)).isEqualTo("O123")
}

round-trip 30건, 기본값 20건, 필수 파라미터 null 체크 11건, multi-path 분기 9건. 이번 리팩토링에서 추가된 네비게이션 관련 테스트만 112개다. 검증의 단위가 "자기 자신과의 라운드트립"이 아니라 "IntentGenerator 계약과의 정합성"이라는 점이 중요하다.

6-C. Resolver는 IntentGenerator를 경유한다 — 한 가지 예외만 빼고

매직 스트링이 정렬되면서 Resolver의 표준 패턴도 자연스럽게 정해졌다. 모든 Resolver는 Destination.toUri()로 URI를 만들고, 그 URI를 IntentGenerator.generateIntent()에 위임한다.

class ProductDetailResolver @Inject constructor(
    private val intentGenerator: ProductIntentGenerator,
) : ScreenResolver<Destination.Screen.ProductDetail> {
    override fun resolve(ctx: Context, dest: Destination.Screen.ProductDetail): Intent {
        val uri = Destination.Screen.ProductDetail.toUri(dest)
        return intentGenerator.generateIntent(ctx, uri)
    }
}

이 패턴을 표준으로 정한 이유는 로그인 정책의 일관성이다. IntentGenerator.generateIntent()는 내부에서 generateIntentBasedOnLogin()을 호출한다. 로그인이 필요한 화면이면 LoginActivity Intent를 반환해, 로그인 후 원래 화면으로 redirect되게 만든다.

Resolver가 IntentGenerator를 거치지 않으면 이 로그인 체크가 우회된다. 같은 화면이 외부 URL로 들어올 때와 코드에서 직접 호출될 때 정책이 갈리는 비대칭이 생긴다. IntentGenerator 경유를 표준으로 두면 두 진입의 정책이 같은 길을 거친다.

예외는 LoginResolver 하나다. Destination.Login.needsAdultCheck라는 capability flag를 받기 때문이다. 성인 인증을 강제로 띄우라는 내부 신호인데, 외부 URL에서 이 flag를 받으면 안 된다 — URL 조작으로 인증 흐름이 위조될 수 있다. 그래서 LoginResolver는 IntentGenerator를 거치지 않고 flag를 LoginActivity에 직접 전달한다. toUri()도 의도적으로 이 flag를 URI에 포함하지 않는다.

data class Login(val needsAdultCheck: Boolean = false) : Screen {
    companion object : DeepLinkSpec<Login> {
        override fun toUri(destination: Login): Uri = buildDeepLink {
            host(DeepLinkHost.LOGIN)
            // needsAdultCheck 는 의도적으로 URI 비노출 — URL 위조 차단
        }
    }
}

예외가 정당화되는 화면("내부에서만 만들 수 있어야 하는 신호를 가진 화면")이 있을 수 있다는 것이 분리 자체를 정당화한다.

다음 목적지

이 리팩토링의 표면적 목적은 Delegator 제거였지만, 더 큰 의도는 Compose Navigation으로의 점진적 전환 발판을 마련하는 것이었다. 그 약속은 유효한가.

유효하다. Destination.Screen.ProductDetail(productNo = 123L)은 Compose Navigation 2.8+의 @Serializable data class ProductDetail(val productNo: Long) 라우트와 구조적으로 동일하다. Resolver를 NavGraphBuilder.composable { }로 교체하고, DestinationNavigator가 NavController를 직접 호출하도록 바꾸면 점진적 전환이 가능하다. UriNavigator 라인은 변경할 필요가 없다 — 외부 URL은 여전히 같은 길로 들어온다.

다만 51개 Activity가 그대로 남아 있다. 전면 전환은 그 51개를 모두 Composable로 옮기는 작업과 같다. 이번 리팩토링이 그 작업의 시작점이 되었지만, 끝은 아직 멀다.

핵심 정리
  • 거대 리팩토링은 단계 분할이 곧 설계다  새 모듈 자리 만들기 → 모델·Resolver 도입 → 호출부 마이그레이션 → 책임 분리 → 모듈 재배치 → 정제. 각 단계는 다음 단계의 전제 조건만 만들고 끝낸다.
  • 내부 진입과 외부 진입은 다른 책임  DestinationNavigator(타입 검증·컴파일 타임)와 UriNavigator(URL 파싱·로그인 정책·fallback)를 같은 파이프라인에 묶으면 한쪽이 다른 쪽의 정책을 떠안는다.
  • 모듈화는 단순 파일 이동이 아니다  파일 위치를 바꾸는 결정 하나가 의존성 역전 인터페이스 3개, KSP 멀티모듈 설정, 매직 스트링 상수 체계, 키 정합성 검증 테스트로 번졌다.
  • 같은 자리에 모이는 매직 스트링은 같은 상수를 본다  Destination.toUri()와 IntentGenerator의 @DeepLink가 같은 DeepLinkHost·DeepLinkQueryParam을 참조하게 만들면, 같은 상수를 못 쓰는 자리가 곧 정합성이 어긋난 자리가 된다.

이 패턴이 적합한 경우. Activity 기반 아키텍처를 유지하면서 네비게이션 시스템을 통합하려는 앱. :app이 모든 Resolver/IntentGenerator를 떠안고 있는 멀티모듈 구조. 외부 딥링크와 내부 호출의 정책 일관성이 필요한 앱.

적합하지 않은 경우. 이미 단일 Activity + Compose Navigation 전환을 완료한 앱(이 글 전체가 우회로일 뿐). 화면 10개 미만의 소규모 앱(Resolver·Module 분할 비용이 본체보다 크다). WebView 중심 하이브리드 앱(네이티브 네비게이션 레이어가 얇으면 이 구조가 과하다).
