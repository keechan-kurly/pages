Claude Code에 "ProductListViewModel.kt 120번째 줄을 고쳐줘"라고 쓰려면 먼저 그 줄을 봐야 한다. 그래서 Android Studio로 넘어가 Double Shift를 누른다. 고친 코드를 기기에 올렸는데 크래시가 나면 다시 IDE로 가서 Logcat을 연다.

컴파일 확인을 맡기면 문제가 하나 더 생긴다. Gradle 빌드 한 번이 많게는 1,800줄을 출력하고, 그 출력이 대화 컨텍스트에 그대로 쌓인다. 판단에 필요한 줄은 열 줄 남짓이다. 우리 저장소는 push 전 컴파일 검증을 의무로 두고 있어서 이 호출이 자주 반복된다.

여기까지는 불편이다. 불편이 사고로 이어지는 지점은 Git이다. 나는 Claude Code 개인 지침(~/.claude/CLAUDE.md)에 "커밋은 사용자가 명시적으로 요청할 때만 한다", "브랜치명은 작업 시작 때 한 번 읽어 고정한다" 같은 규칙을 적어 두었다. 세션이 짧을 때는 지켜진다. 세션이 길어지면 문장은 컨텍스트 뒤로 밀린다. 실제로 세션 도중 바뀐 브랜치를 모른 채 PR을 연 일이 있었고, set -e를 믿고 이어 쓴 commit과 push가 중간 실패를 지나쳐 부분 커밋을 올린 일도 있었다.

cc-studio는 IDE 전환과 Git 사고를 Claude Code 안에서 해결하기 위해 만든 mod 세트다. 전체를 제어하는 허브 하나와 기능 mod 다섯으로 구성되며, 파일 검색, 기기 로그, 빌드 출력, Git 관문과 브랜치 밴드를 /cc-studio 명령 하나로 활성화한다.

이 글은 다섯 단계로 진행한다. 먼저 mod가 무엇인지 설명하고 설치와 사용법을 소개한다. 이어서 다섯 mod가 각각 무엇을 바꾸는지, 다섯 mod를 하나의 명령으로 제어하는 방법을 설명한다. 마지막으로 만들면서 틀린 가설 다섯 개와 이 도구의 한계를 정리한다.

1. mod는 Claude Code 프로세스 안에서 실행되는 함수다

Claude Code에는 기존에도 훅(hook)이 있었다. settings 파일에 셸 명령, HTTP 요청, MCP 도구 호출, 프롬프트나 서브에이전트를 적어 두면 PreToolUse 같은 시점에 실행된다[1]. 이 훅은 Claude Code 외부에서 실행된다. 명령을 막거나 인자를 바꿀 수는 있지만 화면에 무언가를 그릴 수는 없다.

mod는 이와 다른 방식으로 동작한다. 공식 문서는 mod를 이렇게 정의한다.

"A mod is a plugin that changes how Claude Code looks and behaves. It's made of JavaScript or TypeScript event handlers: …"[2]

mod의 훅은 Claude Code 프로세스 안에서 호출되는 함수다. early access 기간에는 활성화 플래그 이름(CLAUDE_CODE_ENABLE_FUNCTION_HOOKS)대로 function hooks라고 불렸다. 이 글은 mod로 통일하고, mod가 등록한 이벤트 핸들러를 훅이라 부른다.

next(e)는 OkHttp의 chain.proceed다

Android 개발자에게 가장 가까운 비유는 OkHttp Interceptor다. 인터셉터는 chain.proceed(request)를 부르기 전에 요청을 바꾸고, 부른 뒤에 응답을 바꾸고, 아예 부르지 않고 응답을 직접 만들 수도 있다. mod 훅도 같은 세 가지를 한다. 이벤트를 관찰하고(observe), 고쳐서 넘기고(rewrite), 직접 답한다(answer)[3].

export const register: Register = on => {
  on('tool.call', { tool: 'Bash' }, async ($, e, next) => {
    if (/\bgit\s+stash\s+store\b/.test(e.command)) {
      // answer: next 를 부르지 않으면 명령은 실행되지 않는다
      return { deny: 'refs/stash 를 덮어써 기존 stash 를 잃는다' }
    }
    const result = await next(e)      // 실제 실행
    $.ui.log('git 명령 실행됨')        // observe: 실행 뒤 기록
    return result
  })
}

이 코드는 설명용 예시다. 실제 cs-gate도 차단, 실행, 실행 뒤 검사의 세 단계로 구성되어 있다. $는 mods API이고, 화면에 그리기, 프로세스 실행, 도구 등록은 모두 이 객체를 거친다. 그래서 claude plugin validate가 실행하지 않고도 mod가 무엇을 호출하는지 나열할 수 있다.

cc-studio는 Claude Code 2.1.278부터 2.1.286까지, early access 기간에 개발했다. 당시에는 CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1을 설정해야 mod가 로드됐다. 공식 문서에 따르면 2.1.287부터 mod는 기본으로 켜지고 이 변수는 값과 무관하게 무시된다[4]. 이 글의 실측은 2.1.278부터 2.1.287 사이 빌드에서 얻은 것이다.

요약

mod는 Claude Code 안에서 호출되는 이벤트 핸들러다. next(e)를 부르는 방식에 따라 관찰, 재작성, 직접 응답을 고르고, $를 통해 pane, band, toast와 도구를 만든다.

2. 설치와 사용: 명시적으로 활성화할 때만 동작한다

허브 하나와 기능 mod 다섯, 모두 여섯 개의 플러그인은 저장소의 .claude/skills/ 아래에 같은 수준으로 위치한다. Claude Code는 이 디렉터리 바로 아래의 하위 디렉터리를 자동으로 탐색해 로드하므로 marketplace 등록이 필요 없다. 팀원은 git pull 뒤 /reload-plugins만 하면 된다.

/cc-studio                  # 다섯 mod를 모두 활성화한다
/cc-studio off              # 다섯 mod를 모두 비활성화한다
/cc-studio gradle logcat    # 지정한 mod만 활성화한다 (나머지는 유지)
/cc-studio off logcat       # 지정한 mod만 비활성화한다
/cc-studio status           # 상태만 조회한다

활성화하면 허브가 변경된 동작을 한 문장씩 요약해 출력한다. 예를 들어 "Gradle 빌드 출력은 핵심 내용만 몇 줄로 요약해서 보여드리고, 전체 로그는 Build 탭에서 확인하실 수 있도록 제공합니다." 같은 문장이다. 출력에서 플러그인 이름과 ON/OFF 표시는 의도적으로 제외했다. cs-gradle이라는 이름만으로는 그것이 무엇을 하는지 알 수 없기 때문이다.

왜 기본값이 비활성 상태인가

플러그인은 세션이 시작할 때 로드된다. 로드 자체는 막을 수 없으므로 로드는 하되 동작은 비활성화해 둔다. 새 세션에서 다섯 mod는 항상 비활성 상태로 시작한다. cs-logcat README는 그 이유를 "로그 창을 묻지도 않고 띄우는 건 주제넘다"고 적는다.

활성화 여부 확인

early access 빌드에서 가장 혼란스러웠던 점은 플래그가 꺼져 있을 때 아무 안내도 없다는 것이었다. 다섯 mod가 커맨드 목록에서 모두 사라졌지만 오류나 경고는 없었다. 그런데 claude plugin list는 같은 상태에서 ✔ loaded를 표시했다. 이 표시는 플러그인 디렉터리를 인식했다는 의미일 뿐, 훅이 실행 중이라는 의미가 아니었다. 지금 빌드에서는 /plugin 화면의 N mod active 줄로 실제 로드된 mod를 확인할 수 있다[5].

3. 다섯 mod가 바꾸는 것

다섯은 모두 Android Studio에 대응하는 기능이 있다. 이 대응이 설계의 출발점이었다. 같은 작업의 동작이 두 도구에서 다르면 사용자가 매번 다시 익혀야 한다.

cs-finder: 파일 검색 pane과 open_tabs 도구

타이핑하면 파일 이름을 fuzzy 검색한다. prodlistvm을 치면 ProductListViewModel.kt가 1위로 올라와야 Double Shift와 같은 결과를 얻을 수 있다. 이를 위해 채점에서 파일명 일치를 가산점이 아니라 별도 등급으로 둔다. 경로는 /와 _로 가득해 단어 경계 보너스가 끝없이 누적되므로, 가산점 방식이면 경로 일치가 파일명 일치보다 앞선다.

고른 파일은 탭으로 열리고, 탭 안에서 단어를 찾아 이동한다. 찾은 줄은 화면 맨 위가 아니라 위에서 1/3 지점에 표시된다. 그 줄이 속한 함수 시그니처가 함께 보여야 맥락을 파악할 수 있다.

가장 유용한 기능은 Claude와 pane이 같은 위치 표기를 공유하는 것이다. Claude는 코드를 Foo.kt:120으로 가리킨다. 그 표기를 검색란에 붙여넣으면 그 줄로 열린다. 반대로 v를 누르면 지금 보는 범위가 path:120-160 형태로 프롬프트에 들어간다. pane이 출력한 표기를 pane이 다시 입력으로 받을 수 있다.

경로를 입력하지 않아도 된다. cs-finder는 open_tabs 도구를 등록하고, 사용자가 "이 파일", "여기"라고 하면 Claude가 이 도구를 호출한다.

사용자가 finder pane 에 열어 둔 파일:
- features/product/ProductListViewModel.kt — 120~160줄을 보고 있다  ← 지금 보는 파일
- app/src/main/java/com/example/HomeActivity.kt
사용자가 "이 파일" · "여기" · "이 코드" 라고 하면 지금 보는 파일을 가리킨다.

경로와 줄 번호만 제공하고 파일 내용은 제공하지 않는다. 내용은 Claude가 이어서 직접 읽는다.

cs-logcat: 기기 하나에 스트림 하나

adb logcat은 끝나지 않는 스트림이라 Bash 도구로는 실행할 수 없다. 타임아웃이 발생하거나 세션을 점유한다. $.process.spawn이 이런 장시간 스트림을 위한 API다.

const child = $.process.spawn({
  // -T 1 로 과거를 걷어낸다. -s 없이는 기기 두 대가 붙은 순간 전부 실패한다
  argv: ['adb', '-s', device, 'logcat', '-v', 'threadtime', '-T', '1'],
})
for await (const chunk of child) {
  for (const raw of splitter.push(chunk.text)) {   // 줄 중간에서 끊긴 조각을 잇는다
    const entry = parseLine(raw)
    const app = pids.get(entry.pid)               // 추적 대상이 아닌 줄은 버린다
    // ...
  }
}

처음에는 앱마다 adb logcat --pid로 스트림을 연결하고 해제하는 구조였다. 이 구조에는 세 가지 문제가 동시에 있었다. --pid 스트림은 프로세스가 종료돼도 스스로 끝나지 않았고, 앱을 재시작하면 pid가 바뀌어 다시 연결해야 했으며, 연결과 해제 사이에 상태가 이전 루프의 finally와 경쟁했다. 세 번 수정했지만 매번 다른 지점에서 문제가 재발했다.

그래서 기기 하나에 스트림 하나를 연결해 두고, 어느 앱의 로그인지는 각 줄에 포함된 pid로 구분하도록 바꿨다. pid와 패키지의 대응표는 5초마다 ps로 갱신한다. 연결과 해제가 없어지자 세 문제가 함께 해결됐다. store와 beta 플레이버를 번갈아 실행해도 다음 ps 한 번으로 로그 수집이 이어진다.

크래시는 pane이 아니라 toast로 알린다. 이유는 5절에서 다룬다. Claude는 read_logcat({ grep, lines })으로 버퍼를 조회해 재현 없이 크래시 스택을 읽는다.

cs-gradle: 실행 결과 대신 명령을 재작성한다

Gradle 출력을 줄이는 가장 쉬운 방법은 await next(e)로 실행한 뒤 결과를 다듬는 것이다. cs-gradle은 이 방식을 쓰지 않았다. 만들 당시 빌드의 타입 선언에서는 Bash 도구의 결과 타입이 unknown이라 결과를 안전하게 갈아끼울 수 없었다. 반면 바꾼 명령을 next({...e, command})로 넘기는 경로는 타입이 온전히 잡혔다. 그래서 명령 자체를 바꿔 넘긴다.

# 원래 명령
./gradlew :features:compileDebugKotlin

# cs-gradle 이 next 에 넘기는 명령
{ ./gradlew :features:compileDebugKotlin
} > "$LOG" 2>&1; __rc=$?; awk -f "$LENS" "$LOG";
echo "full log → $LOG (N lines)"; exit $__rc

로그는 파일로 저장하고 awk가 추출한 줄만 대화에 전달한다. Kotlin 진단(e:, w:), * What went wrong: 블록, BUILD FAILED in … 요약만 남긴다. 경고는 5건까지만 포함한다. 26줄짜리 샘플 출력에서 잰 결과는 10줄이었다. 큰 빌드라도 남는 것은 진단과 요약뿐이라, 에러가 몇 개 안 되면 출력 길이가 비슷하게 유지된다. exit $__rc로 종료 코드를 보존하는 것이 핵심이다. 이것을 놓치면 실패한 빌드가 성공으로 보고된다.

Gradle 명령이 감지되면 Build 탭을 전면에 표시하도록 요청하며, 전체 로그는 이 탭에서 확인한다.

cs-gate: 문장 규칙을 관문으로

cs-gate는 CLAUDE.md의 Git 안전 규칙을 문장이 아니라 관문으로 강제한다. 응답은 세 가지뿐이다.

응답언제예
차단 { deny }항상 틀린 명령git stash store, 쓰기 명령 안의 $(git branch --show-current)
승인 $.ui.ask판단이 필요한 명령commit, push, checkout -b, reset --hard, rebase
교정 next({...e, command})정답이 명확한 실수;로 이은 Git 명령 체인을 &&로 연결, 고정 /tmp 경로를 세션 디렉터리로

승인에는 조건이 하나 붙는다. 턴의 첫 Git 호출이라면, 사용자가 그 동사를 직접 요청했을 때 묻지 않는다. "커밋해줘"라고 했는데 다이얼로그를 또 띄우면 관문이 불필요한 확인 절차가 된다. 같은 턴에서 이어지는 호출에도 이 판정이 그대로 맞는지는 아직 확인하지 못했다. 다이얼로그를 띄울 때는 브랜치, upstream, staged와 unstaged 수를 함께 보여준다. unstaged가 있으면 "커밋에서 빠집니다"라고 적는다.

permission 규칙 Bash(git push:*)와의 차이는 조사할 수 있다는 점이다. 규칙은 명령 문자열만 본다. 훅은 push 전에 git fetch를 돌려 원격이 앞서 있는지 확인하고, 커밋 뒤에는 unstaged 잔여를 세어 Claude에게 알린다. 우리 PR 브랜치에는 의존성 갱신 봇 같은 자동화가 커밋을 추가하는 일이 잦다. 이 확인은 그 상황에 대비한 것이다.

관문에는 한 가지가 더 필요하다. 공식 문서에 따르면 .catch 없는 훅이 예외를 던지면 Claude Code는 그 훅을 건너뛰고 다음 핸들러를 실행한다[6]. 관문에 오류가 나면 명령이 그대로 실행된다는 뜻이다. 그래서 fail-closed로 처리한다.

on('tool.call', { tool: 'Bash' }, guard).catch(($, e, next) => {
  if (!awake) return next(e)
  // 사후 검사에서 터졌다면 명령은 이미 실행됐다. deny 하면 "막았다" 는 거짓 보고가 된다
  if (next.called) return next(e)
  return { deny: 'git-gate: 게이트 오류. 안전을 위해 차단했습니다.' }
})

cs-band: 사용자와 Claude에게 같은 Git 상태를 제공한다

cs-band는 프롬프트 바로 위에 한 줄을 그린다.

⎇ .../ABC-1/task/x   ↑2 ↓3 origin   ● +2 ~1 ?3   워크트리 pr-1234
⎇ master   ⚠ 시작 시 develop   ↑0 ↓3 upstream   ○ clean
⎇ .../ABC-1/task/x   ⚠ upstream=origin/develop   ● ~2   워크트리 main

이 밴드의 주 목적은 경고다. 세션 시작 때 기록한 브랜치와 현재 브랜치가 다르면 ⚠ 시작 시 develop이 빨간색으로 표시된다. 기능 브랜치의 upstream이 베이스 브랜치로 잘못 설정되어 있어도 표시된다. 도입에서 말한 브랜치 사고와 워크트리 upstream 오설정은 이 경고로 미리 드러났어야 했다. 부분 커밋 사고는 밴드가 아니라 cs-gate의 체인 교정이 막는다.

같은 값을 where_am_i 도구로 Claude에게도 제공한다. 도구 설명에는 "커밋, push, PR 생성 직전에 반드시 호출한다"고 명시했다. 대화 앞부분에 포함된 Git 정보는 세션 도중 브랜치가 바뀌면 실제 상태와 달라진다. where_am_i는 응답 직전에 Git 상태를 다시 읽으므로 항상 최신 값을 반환한다.

한 줄짜리 UI라서 폭 계산이 의외로 까다로웠다. 한글은 터미널에서 두 칸인데 String.length로 세면 한 칸으로 계산되어 밴드가 화면 폭을 넘는다. 긴 브랜치 이름을 upstream이 한 번 더 쓰는 문제도 있었다. 브랜치는 티켓 키가 보이는 데까지만 뒤쪽 조각을 남기고, upstream이 같은 이름을 가리키면 remote 이름만 쓰도록 바꿔 195칸을 98칸으로 줄였다. 단 밴드에서만 줄인다. where_am_i는 커밋 직전에 Claude가 읽는 값이라 항상 전체 이름을 반환한다.

4. 다섯 mod를 하나의 명령으로: 공유 상태 없이 활성화하기

다섯 mod는 서로 독립된 플러그인이다. 서로의 코드를 import할 수 없고, 서로를 조회할 API도 없다. 그런데 /cc-studio 명령 하나로 다섯 mod가 함께 활성화되어야 한다.

답은 이벤트가 전역이라는 데 있었다. 허브가 다섯에게 명령을 전달하지 않는다. 다섯 mod가 같은 command.run 이벤트를 각자 처리하고 같은 인자를 해석한다.

/cc-studio gradle logcatcommand.run 이벤트 1회

cc-studio먼저 next(e)

이 구조에는 두 가지 이점이 있다. 로드 순서에 의존하지 않고, 하나가 로드에 실패해도 나머지는 정상적으로 활성화된다. 대신 인자를 해석하는 규칙(wake.ts)을 다섯 플러그인이 각자 복제해 포함해야 한다. 규칙을 고치면 다섯 곳을 함께 고쳐야 하므로 규칙을 작게 유지했다.

export function decide(args: string, aliases: readonly string[]): Decision {
  const words = args.trim().toLowerCase().split(/\s+/).filter(w => w !== '')
  if (words[0] === 'status') return { statusOnly: true, names: [] }

  // on, off 는 어느 자리에 있어도 읽는다
  const off = words.includes('off')
  const names = words.filter(w => w !== 'on' && w !== 'off')
  if (names.length === 0) return { awake: !off, statusOnly: false, names }

  const named = names.some(w => aliases.includes(w))
  return named ? { awake: !off, statusOnly: false, names } : { statusOnly: false, names }
}

이 주석에는 버그 하나의 수정 이력이 담겨 있다. 처음에는 off를 첫 단어에서만 찾았다. 그러자 /cc-studio gradle off에서 off가 mod 이름으로 처리되었고, 비활성화 명령이 오히려 cs-gradle을 활성화했다.

허브의 응답 문장도 이 구조를 따른다. 허브는 다섯의 실제 상태를 알 수 없고 자기가 보낸 명령만 안다. 그래서 "켜졌습니다"가 아니라 "2/5에 켜라고 전달했습니다"라고 답한다. 설치되지 않은 mod도 똑같이 표시되므로, 활성화되었다고 단정하면 존재하지 않는 안전장치를 있다고 안내하게 된다.

활성 상태를 어디에 저장할까

처음에는 모듈 변수 let awake = false에 뒀다. 개발 중 파일을 저장하면 모듈이 다시 적재되면서 변수가 초기화됐다. cs-gate라면 파일 저장 한 번에 안전장치가 경고 없이 해제된다. 그래서 값을 플러그인 저장소 $.store로 옮겼다.

이 방식도 문제가 있었다. 옆 세션에서 허브 커맨드(당시 이름 /claude-studio)를 실행하자 그 기록이 이 세션의 기록을 덮어썼고, 이 세션의 mod가 리로드 뒤 비활성 상태로 남았다. Logcat 탭에는 "연결된 Device 없음"만 표시되었다. 공식 문서는 원인을 분명히 적고 있다. $.store는 세션 사이에 남는 저장소이고, 같은 머신의 모든 세션이 하나를 함께 쓴다[8].

저장 위치유지 기간활성 상태 저장에 적합한가
모듈 변수모듈이 다시 적재될 때까지부적합. 파일 저장만으로 초기화된다
$.store세션을 넘어 남고, 모든 세션이 공유한다부적합. 다른 세션이 값을 덮어쓴다
$.state세션이 끝나거나 /clear, /resume, /branch를 실행할 때까지. 리로드는 넘긴다가장 적합. 새 세션은 항상 비활성 상태로 시작한다. 단 /clear 뒤 리로드가 일어나면 비활성 상태로 돌아간다

최종적으로 허브와 다섯 mod 모두 $.state로 옮겼다. 앞서 인용한 공식 문서의 같은 절도 세션 동안만 유지되고 리로드를 넘기는 값의 저장 위치로 $.state를 안내한다. cs-band가 세션 시작 때 기록하는 시작 브랜치도 같은 이유로 $.state에 저장한다.

이름과 구조도 바뀌었다

허브의 원래 이름은 claude-studio였다. CLI 2.1.287부터 claude-로 시작하는 플러그인 이름이 예약어가 되어 claude plugin validate가 거부했다. Anthropic 것처럼 보이는 이름을 막는 규칙이다. 커맨드도 /cc-studio로 함께 옮겼다. 커맨드 이름과 플러그인 이름이 다르면 사용자가 어느 쪽이 맞는지 매번 확인해야 한다.

디렉터리 구조도 바뀌었다. 한때 다섯 mod를 cc-studio/cs-*처럼 허브 하위에 두었는데, 자동 로드는 바로 아래의 하위 디렉터리만 탐색하기 때문에 다섯 mod가 로드되지 않았다. marketplace를 따로 등록하자 그 경로가 절대경로로 기록돼 다른 팀원의 머신에서는 경로가 맞지 않았다. 그래서 허브와 다섯 mod를 같은 수준에 나란히 두고, 그룹 구분은 디렉터리 대신 cs- 접두사로 표현한다.

5. 만들면서 틀린 가설 다섯 개

만들 당시 mods는 정식 출시 전이었고, 참고 자료는 엔진 타입 선언과 내장 mod 소스가 중심이었다. 그래서 가설을 세우고 실측하는 일을 여러 번 반복했다. 다음 개발자가 같은 문제에 시간을 쓰지 않도록 그중 다섯 가지를 정리한다.

가설 1. "focus: true로 열면 그 탭이 전면에 표시된다"

cs-finder는 처음에 파일마다 pane을 열어 엔진의 탭 기능에 맡겼다. 탭은 생겼지만 전면에 표시되지 않았다. 검색 pane이 키보드 포커스를 가진 상태에서 새 pane을 focus: true로 열었기 때문이다. 공식 문서는 focus를 이렇게 설명한다.

"Claude Code grants focus: true only while the prompt is empty and nothing else has keyboard focus."[9]

focus는 요청이지 보장이 아니다. 그리고 $.ui에는 다른 pane을 전면으로 전환하는 API가 없다. 해결 방법은 두 가지였다. cs-finder는 pane 하나에 탭 바를 직접 그려 탭 전환을 직접 제어했다. cs-logcat은 크래시 같은 즉시성 있는 신호를 pane에 맡기지 않고 toast와 상태줄에 넘겼다. pane은 사용자가 필요할 때 열어 확인하는 영역이므로, 즉시 알려야 하는 신호는 toast와 상태줄로 전달한다.

가설 2. "큰 파일 스크롤이 느린 건 그리는 양 때문이다"

수천 줄 파일에서 스크롤이 끊겼다. 네 가지 가설을 차례로 실측했고 모두 틀렸다.

가설검증결과
구문 강조 span 수강조 끄기 토글로 A/B무효
줄 길이, 빈 줄파일 통계 비교무효
스크롤 중 재렌더멈춘 뒤로 미룸무효
창 단위 렌더 + 스페이서내용만 화면 크기로, 높이는 스페이서로 유지무효

마지막 실험이 결정적이었다. 그리는 내용을 1/4로 줄여도 전체 높이를 유지하는 한 비용이 그대로였다. 비용은 그리는 양이 아니라 엔진이 큰 트리 위에서 표시 영역을 이동하는 작업 자체였다.

답은 Claude Code에 내장된 /diff mod의 공개 소스에 있었다[10]. diff는 사용자가 dock pane에서 스크롤한 이벤트를 엔진에 넘기지 않는다. ui.scroll 이벤트를 받으면 next를 호출하지 않고 직접 처리하며, 자체 스크롤 위치만 갱신해 화면에 보이는 부분만 그린다. 그 밖의 스크롤은 엔진에 넘긴다.

on('ui.scroll', { requestId: Names.PANE_ID }, ($, e, next) => {
  const isOwnBody = e.origin.kind === 'person' && model.placement === 'dock'
  if (!isOwnBody || !host) {
    return next(e)
  }
  const isOverList = Views.isWheelOverList(model, e)
  model = {
    ...model,
    place: isOverList
      ? Views.listScrolledBy(model, e.by)
      : Views.bodyScrolledBy(model, e),
  }
  host.invalidate()
  return {}
})
anthropics/claude-code mods/diff/hooks/register.ts 908행. 빈 줄만 줄였다

마지막 return {}가 핵심이다. next를 부르지 않으니 엔진 창은 움직이지 않는다. 트리가 늘 화면 높이만 하니 큰 트리를 훑을 일이 없다. 이 방식으로 바꾸자 스크롤이 매끄러워졌고, 부수 효과로 스크롤 앵커, 스페이서, 디바운스와 재시도 코드가 모두 제거됐다. cs-logcat의 과거 로그 스크롤도 같은 방식이다. 머리글과 RESUME, CLEAR 버튼이 고정되는 것도 이 덕분이다.

교훈은 단순하다. 같은 엔진에서 정상 동작하는 참조 구현을 먼저 읽는다. 가설을 네 번 세우는 동안 답은 공개 저장소에 있었다.

가설 3. "prompt.context로 열린 탭 목록을 컨텍스트에 추가할 수 있다"

cs-finder의 2차 목표는 pane에서 보는 것을 Claude도 알게 하는 것이었다. 처음 시도한 방법은 prompt.context 이벤트에서 열린 탭 목록을 컨텍스트에 덧붙이는 것이었다. 컨텍스트에는 아무것도 추가되지 않았다. 덧붙이는 필드를 바꿔 다시 시도했지만 결과는 같았다.

두 번 추측한 뒤에야 claude --debug를 켰다. 로그에는 한 줄이 있었다.

finder: prompt.context bypassed by sec-default (tier user); beneath runs

훅은 등록됐지만 호출되지 않았다. 로그가 가리킨 것은 Claude Code에 내장된 guard인 sec-default였다. 공식 문서 기준으로 이 guard는 managed settings가 있는 머신이나 Team, Enterprise 플랜으로 로그인한 환경에서만 로드된다[11]. 우리 환경에서는 로드되어 있었지만, 독자의 환경에서는 로드되지 않을 수 있다. 문서는 guard의 보호 범위를 시스템 프롬프트와 조직이 관리하는 지시 파일로 적고 있고, prompt.context를 막는다고 명시하지는 않는다. 우리가 확인한 것은 debug 로그의 그 한 줄까지다. 사용자가 이 guard를 끌 수는 없으므로 다른 방법이 필요했다.

그래서 컨텍스트에 직접 추가하는 대신 Claude가 필요할 때 조회하도록 바꿨다. 그것이 open_tabs 도구다. 결과적으로 이 방식이 더 나았다. 필요한 턴에만 컨텍스트에 포함되고, 그 밖의 턴에는 컨텍스트를 차지하지 않는다. 대신 도구 설명이 매 세션 컨텍스트에 포함된다.

교훈은 이렇다. 훅이 아무 동작도 하지 않으면 추측하지 말고 --debug부터 켠다. 로그 한 줄로 확인하는 비용이 두 번의 잘못된 추측보다 적었다.

가설 4. "Git 명령은 정규식으로 충분히 판별할 수 있다"

cs-gate와 cs-gradle의 첫 버전은 명령 문자열에 정규식을 걸었다. PR 리뷰에서 이 방식을 우회하는 입력이 다수 발견됐다.

입력정규식 판정실제
git -C ../other commitcommit 아님 (통과)다른 저장소의 커밋
git --no-pager pushpush 아님 (통과)push
echo 'git stash store'차단문자열 출력일 뿐
sudo -u root git pushroot를 명령으로 읽음 (통과)push
./gradlew test -Pmask=$((1 | 2))파이프로 읽고 tee를 끼움산술 치환 안의 |

해법은 정규식을 늘리는 것이 아니라 판정 단위를 바꾸는 것이었다. 명령을 셸 단어로 가르고, 따옴표, $(…), 백틱과 서브셸의 깊이를 스택으로 따라가 실제로 실행되는 Git 호출을 먼저 뽑는다. 규칙은 그렇게 뽑은 호출마다 건다. -C, cd, --git-dir로 지정한 저장소도 따라가서 그 저장소에서 fetch와 status를 실행한다.

사용자의 말을 읽는 쪽도 같은 문제를 겪었다. "커밋하지 마"를 커밋 승인으로 읽었고, "커밋 규칙을 설명해줘"도 승인으로 읽었다. don't commit or push는 push 승인이 됐다. 지금은 키워드 뒤에 조사와 접속어만 지나 요청 동사가 와야 승인으로 보고, 부정어가 붙거나 묻는 문장이면 승인이 아니다.

그래도 이 판정은 완벽하지 않다. 공식 문서도 명령 텍스트를 맞추는 훅은 Claude에게 주는 환기(reminder)로 다루라고 쓴다[12]. 보호 브랜치 같은 최종 방어선은 Git 호스트에 둔다. cs-gate는 그 앞에서 세션 안의 실수를 줄이는 장치다.

가설 5. "테스트가 통과하면 동작한다"

허브와 다섯 mod의 테스트는 README 기준 290건이다. 순수 함수(채점, 줄 분해, 인자 해석, 셸 파싱, 밴드 조립)는 엔진 없이 테스트하고, 훅은 claude plugin test의 테스트 킷으로 이벤트를 발화해 테스트한다.

그런데 테스트 킷은 화면을 그리지 않는다. 레이아웃된 요소를 겨냥하는 스크롤, 실제 포커스와 입력 필드의 동작은 테스트로 검증되지 않는다. 입력 필드가 제출 뒤 검색어를 지우는 동작도 실기기 터미널에서 처음 발견했다. 그래서 순회 로직은 실패 로그에 찍힌 줄 번호로 검증하고, 실제 스크롤과 포커스는 실기 확인의 몫으로 남겼다. 테스트가 검증하는 범위를 아는 것도 검증의 일부다.

요약

focus는 요청이고, 스크롤 비용은 트리 크기에서 오며, prompt.context는 guard가 막을 수 있다. 셸 명령은 셸 문법으로 호출을 가른 뒤 판정해야 하고, 테스트 킷은 화면을 그리지 않는다. 이 중 앞의 셋은 공식 문서, 공개된 내장 mod 소스나 --debug 로그를 먼저 봤다면 더 빨리 풀렸다.

6. 대안과 한계

다른 도구로도 되는 일

permission 규칙은 코드가 필요 없다. Bash(git push:*)를 ask로 두면 push마다 묻는다. 고정된 명령을 막는 데는 이쪽이 낫다. 다만 "원격이 앞서 있으면", "사용자가 이번 턴에 말하지 않았으면" 같은 조건은 문자열로 쓸 수 없다.

settings 훅(PreToolUse)도 명령을 막거나 인자를 바꿀 수 있고, 이미 가진 셸 스크립트를 그대로 쓸 수 있다. 하지만 pane이나 band를 그릴 수 없고, Logcat처럼 끝나지 않는 스트림을 세션 내내 유지할 수 없다.

공식 문서에는 cc-studio가 쓰지 않은 방법도 있다. 허용과 거부만 정하는 판단이라면 tool.check 이벤트가 그 용도다. tool.check는 판정(allow, ask, deny)만 돌려주므로, cs-gate가 하는 명령 재작성과 실행 뒤 잔여 검사는 tool.call에 둘 수밖에 없다. 또 prompt.submit은 Claude만 읽는 줄을 프롬프트에 덧붙일 수 있다[13]. 매 턴 컨텍스트에 추가되는 대신 Claude가 도구를 호출할 필요가 없다. open_tabs 도구와 어느 쪽이 나은지는 쓰임새에 따라 다르다.

IDE 그대로 쓰기가 나은 일도 분명하다. 편집, 디버거, Layout Inspector, 리팩터링은 여전히 Android Studio의 몫이다. cs-finder는 의도적으로 편집 기능을 두지 않았다. cc-studio는 IDE를 대체하는 도구가 아니라, 코드와 로그를 확인하기 위해 IDE로 전환하는 일을 줄이는 도구다.

알려진 한계

  • API가 아직 변경되고 있다. 만드는 동안에도 플러그인 이름 규칙이 바뀌었고, 활성화 방식이 플래그에서 기본값으로 바뀌었다. 릴리즈마다 실측을 다시 확인해야 한다.
  • 활성 상태가 영구적이지 않다. 새 세션은 비활성 상태로 시작하고, /clear나 /resume 뒤 모듈이 다시 로드되면 비활성 상태로 돌아간다. 관문이 꺼진 줄 모르고 작업할 수 있으니 상태줄의 git-gate armed를 확인해야 한다.
  • wake.ts가 다섯 벌 있다. 플러그인끼리 코드를 공유할 수 없어서다. 인자 문법을 바꾸려면 다섯 곳을 함께 고쳐야 한다.
  • 리로드하면 Finder 탭이 사라진다. 열린 탭 목록은 모듈 메모리에 있다. 최근 연 파일 목록은 $.store에 있어서 살아남는다.
  • UI는 터미널과 Desktop 앱에서만 표시된다. VS Code 확장의 채팅 패널이나 claude -p에서는 훅만 실행되고 pane은 그려지지 않는다[14].
  • mod는 사용자 권한으로 실행된다. 샌드박스가 없다. 팀 저장소에 mod를 두면 git pull 한 번으로 모든 팀원의 세션에서 그 코드가 실행된다. 리뷰를 일반 코드보다 엄격하게 해야 한다.

7. 정리

  • 1반복해서 지켜야 하는 규칙은 문장에서 관문으로 옮긴다. CLAUDE.md의 문장은 긴 세션에서 뒤로 밀린다. tool.call 훅은 활성화되어 있는 동안 모델의 기억과 무관하게 매번 검사한다. 단 cs-gate처럼 기본값을 비활성 상태로 두면, 활성화 여부는 사용자가 확인해야 한다.
  • 2UI 영역은 정보의 긴급도로 고른다. 필요할 때 확인하는 정보는 pane, 항상 보여야 하는 정보는 band, 즉시 알려야 하는 정보는 toast와 상태줄에 둔다. 그리고 사용자가 보는 값은 Claude에게도 도구로 제공한다.
  • 3훅이 조용하면 추측하기 전에 --debug와 내장 mod 소스를 본다. 이 프로젝트의 가장 비싼 시간은 이미 답이 있는 곳을 보지 않은 시간이었다.

직접 시작해 보려면 공식 샘플 mod 하나를 claude --plugin-dir로 실행해 보길 권한다[15]. 그다음 자기 CLAUDE.md에서 가장 자주 어겨지는 규칙 하나를 골라 tool.call 훅으로 옮겨 본다. 규칙을 코드로 강제하는 관문 하나가 지침 문장 열 줄보다 확실하다.
