ViewGroup.removeView() 를 부르면 뷰는 parent 에서 제거되고, 다음 프레임부터는 그려지지 않는다. 뷰에 애니메이션이 붙어 있지 않다면 그렇다.

그런데 운영 중인 앱에서 Braze slideup IAM(인앱 메시지)이 닫힌 뒤에도 화면 상단에 남아 있다는 사용자 제보가 들어왔다. 재현해 보니 Braze SDK 로그에는 Closing in-app message view 가 찍혔고, SDK 는 다음 IAM 을 받을 준비까지 마쳤다. SDK 기준으로는 닫혔는데 화면에서는 사라지지 않은 것이다.

재현한 잔상 (Galaxy S21 Ultra, Android 15)

상단 카드 이미 닫힌 IAM 이다. 위쪽이 잘린 채 상태바에 겹쳐 그려진다.

터치 눌러도 반응하지 않는다. Activity 가 새로 만들어져야 사라진다.

이 글은 세 가지 질문에 차례로 답한다. 애니메이션이 붙은 채 제거된 뷰는 어디로 가는가. 그 뷰는 왜 정리되지 않는가. 앱에서는 어떻게 막는가. 원인은 Android 의 mDisappearingChildren 정리 규칙과, Braze SDK 의 두 닫기 경로가 겹치는 타이밍에 있었다.

1. 증상: 닫혔다는데 남아 있는 IAM

제보 내용과 재현한 화면은 공통으로 다섯 가지 특징을 보였다. 다음 IAM 이 겹쳐 뜨는 동작은 SDK 코드로 확인한 것이고, 나머지는 재현 기기에서 관찰했다.

특징관찰
모든 탭에서 보인다하단 탭을 바꿔도 같은 위치에 남는다
터치에 반응하지 않는다잔상을 눌러도 아무 일도 일어나지 않는다
다음 IAM 이 그 위에 뜬다SDK 는 닫힌 것으로 알고 다음 IAM 을 같은 자리에 띄운다
간헐적이다같은 동작을 반복해도 대부분 정상이고 가끔만 남는다
Activity 가 새로 만들어져야 사라진다탭 이동으로는 사라지지 않는다

잔상이 남은 상태에서 dumpsys activity top 으로 view tree 를 떠 보면 잔상에 해당하는 Braze 뷰가 없었다. 화면에는 그려지는데 view tree 와 터치 대상에는 없다. 이 관찰이 원인을 좁히는 출발점이었고, 그 의미는 5장에서 밝힌다.

2. 기각한 가설 둘

첫 제보는 Galaxy S25 Edge(Android 17) 사용자에게서 왔다. 그래서 처음에는 최신 OS 나 특정 제조사의 렌더링 차이를 의심했다. 하지만 팀에서 Android 15 인 Galaxy S21 Ultra 와 Android 17 인 Pixel 10 으로 직접 재현해 보니 두 기기 모두에서 같은 잔상이 남았다. 이 글의 로그와 스크린샷은 모두 Galaxy S21 Ultra 실측이다.

두 번째로 의심한 것은 2026년 10월 14일에 커밋된 검색 탭의 IAM 억제 로직이었다. 검색 탭에 들어오면 InAppMessageSuppressPolicy.DISCARD 정책으로 떠 있던 IAM 을 강제로 닫는데, 개발 빌드에서 이 강제 닫기로 잔상이 생기는 장면도 재현됐다. 그러나 이 로직이 없는 빌드에서도 같은 증상을 팀에서 확인했다. 이 커밋은 아직 배포된 버전에 들어 있지 않으므로, 운영 제보는 이 로직과 무관하게 생긴 것이다.

가설반증
OS 또는 기기 문제Android 15 삼성 기기와 Android 17 Pixel 기기에서 모두 재현
검색 탭 DISCARD 가 원인억제 로직이 없는 빌드에서도 같은 증상

두 가설을 지우고 나니 공통점이 남았다. 재현한 모든 경우에 노출 10초 뒤 시작된 자동 닫기 애니메이션이 도는 도중 다른 닫기가 끼어들었다. 문제는 기기가 아니라 타이밍이었다.

3. 200ms 의 창을 3초로 넓히기

타이밍 버그는 재현 구간이 좁을수록 진단이 어렵다. 자동 닫기 애니메이션은 기본 설정에서 200ms 다. 그 안에 다른 닫기를 정확히 끼워 넣어야 하므로 사람이 손으로 재현하기는 어렵다.

그래서 닫기 애니메이션의 길이만 3초로 늘린 진단 빌드를 만들었다. Braze 는 IAM 애니메이션을 바꿀 수 있는 factory 를 공개 API 로 제공한다.

BrazeInAppMessageManager.getInstance().setCustomInAppMessageAnimationFactory(
    object : DefaultInAppMessageAnimationFactory() {
        override fun getClosingAnimation(inAppMessage: IInAppMessage): Animation? =
            super.getClosingAnimation(inAppMessage)?.apply { duration = 3000L }
    }
)

열림 애니메이션과 닫기 로직은 그대로 두고 닫기 구간만 늘렸다. 원인이 되는 순서는 바꾸지 않고 창만 15배 넓힌 셈이다. 이 빌드로 두 기기 모두에서 사람이 직접 잔상을 재현했다. 원래의 200ms 빌드에서도, 스와이프 닫기가 자동 닫기 시작 뒤 34~172ms 에 들어온 8회는 8회 모두 잔상이 남았다.

진단 빌드에는 IAM 뷰의 상태를 250ms 마다 찍는 로그 프로브도 넣었다. 이 글에 나오는 상태값은 모두 이 프로브의 실측이다.

4. 두 개의 닫기 경로

Braze slideup IAM 은 두 가지 방법으로 닫힌다. 노출 시간이 지나면 자동으로 닫히고, 사용자가 가로로 밀어서 닫을 수도 있다. 두 경로는 모두 DefaultInAppMessageViewWrapper.close() 로 모이지만, animateOut 값에 따라 갈라진다.[1]

override fun close() {
    // ... (접근성 플래그 복원 생략)
    inAppMessageView.removeCallbacks(dismissRunnable)
    inAppMessageViewLifecycleListener.beforeClosed(inAppMessageView, inAppMessage)
    if (inAppMessage.animateOut) {
        isAnimatingClose = true
        setAndStartAnimation(false)   // [글쓴이 주석] 자동 닫기: 애니메이션을 붙이고, 제거는 종료 콜백에 맡긴다
    } else {
        closeInAppMessageView()       // [글쓴이 주석] 스와이프: 바로 parent 에서 뗀다
    }
}

자동 닫기는 위로 올라가는 TranslateAnimation 을 뷰에 붙이고, parent 에서 제거하는 일은 애니메이션 종료 콜백으로 미룬다. 스와이프 닫기는 animateOut = false 로 바꾼 뒤 같은 close() 를 불러 뷰를 바로 제거한다. 이 글에서는 앞의 것을 애니메이션 닫기, 뒤의 것을 즉시 닫기라고 부른다.

문제는 즉시 닫기가 생각보다 늦게 온다는 점이다. 사용자가 손을 떼면 IAM 은 200ms 동안 옆으로 밀리며 투명해지고, 사용자 눈에는 여기서 닫힌다. 하지만 SDK 의 SwipeDismissTouchListener 는 그 뒤에도 보이지 않는 상태로 뷰 높이(이 기기에서 169px)를 1px 까지 줄이는 애니메이션을 200ms 더 돌린다. onDismiss 는 그것이 끝나야 불린다. 실측으로는 손을 뗀 뒤 약 420ms(415~445ms)였다.[2]

그리고 onDismiss 는 애니메이션 닫기가 이미 진행 중인지 확인하지 않는다.

override fun onDismiss(view: View, token: Any?) {
    inAppMessage.animateOut = false
    BrazeInAppMessageManager.getInstance().hideCurrentlyDisplayingInAppMessage(true)
}

그 결과 닫기 애니메이션이 붙어 있는 뷰를 즉시 닫기가 parent 에서 제거하는 상황이 만들어진다. 이제 첫 번째 질문으로 돌아간다. 이렇게 제거된 뷰는 어디로 가는가.

5. 답 1: 뷰는 정리 대기 목록으로 간다

removeView() 의 실제 처리는 ViewGroup.removeViewInternal() 이 맡는다. 여기서 뷰에 애니메이션이 붙어 있는지부터 확인한다.[3]

if (view.getAnimation() != null ||
        (mTransitioningViews != null && mTransitioningViews.contains(view))) {
    addDisappearingView(view);          // [글쓴이 주석] 애니메이션이 있으면 정리 대기 목록으로
} else if (view.mAttachInfo != null) {
    view.dispatchDetachedFromWindow();  // [글쓴이 주석] 없으면 바로 window 에서 분리
}

애니메이션이 붙어 있으면 Android 는 뷰를 window 에서 분리하지 않는다. 일반 자식 목록(mChildren)에서 빼고 mParent 를 null 로 만들지만, 대신 mDisappearingChildren 이라는 별도 목록에 넣는다. 사라지는 애니메이션을 끝까지 보여 주기 위한 설계다. 이 글에서는 이 목록을 정리 대기 목록이라고 부른다.

정리 대기 목록의 뷰는 계속 그려진다. ViewGroup.dispatchDraw() 는 일반 자식을 그린 뒤 이 목록도 순회한다.[4]

// Draw any disappearing views that have animations
if (mDisappearingChildren != null) {
    final ArrayList<View> disappearingChildren = mDisappearingChildren;
    final int disappearingCount = disappearingChildren.size() - 1;
    // Go backwards -- we may delete as animations finish
    for (int i = disappearingCount; i >= 0; i--) {
        final View child = disappearingChildren.get(i);
        more |= drawChild(canvas, child, drawingTime);
    }
}

이 루프는 visibility 를 확인하지 않는다. 목록에 있으면 GONE 이어도 그린다. 반면 터치 이벤트는 mChildren 에만 전달되고, dumpsys 의 view tree 도 mChildren 만 따라간다. 1장에서 본 상태, 즉 보이는데 view tree 와 터치 대상에는 없는 상태가 바로 정리 대기 목록에 있는 뷰의 모습이다.

3초 진단 빌드의 기록도 같은 상태를 보여 준다. 즉시 닫기 직후의 로그다(필드 일부 생략).

VKPROBE : beforeClosed force=false animateOut=false parent=ContentFrameLayout
Braze   : Closing in-app message view
Braze   : Removed view: ...InAppMessageSlideupView{... 0,51-720,53 ...}
Braze   : Resetting after in-app message close.
VKPROBE : t=1000ms parent=false attached=true vis=0 anim=true ... h=2 ...

parent=false 인데 attached=true 다. parent 에서는 제거됐지만 window 에서는 분리되지 않았다. SDK 는 이 시점에 resetAfterInAppMessageClose() 로 닫힘 처리를 끝내고 다음 IAM 을 받을 준비를 한다. 1장의 "다음 IAM 이 그 위에 뜬다"는 증상은 여기서 나온다.

5장 요약

애니메이션이 붙은 채 제거된 뷰는 사라지지 않고 정리 대기 목록으로 간다. 이 목록의 뷰는 visibility 와 무관하게 그려지지만 view tree 와 터치 대상에는 없다.

6. 답 2: 정리 조건이 먼저 사라진다

정리 대기 목록 자체는 버그가 아니다. 애니메이션이 끝나면 뷰는 목록에서 빠져야 한다. 목록에서 빼는 경로는 두 가지다.[5]

  • 애니메이션이 끝났을 때: View.draw() 끝부분이 ViewGroup.finishAnimatingView() 를 부른다. 애니메이션 종료에 따른 정리는 이것뿐이다.
  • parent 가 window 에서 분리될 때: ViewGroup.dispatchDetachedFromWindow() 가 clearDisappearingChildren() 로 목록을 통째로 비운다. Activity 가 종료될 때 이 경로가 실행된다.

평소에는 첫 번째 경로가 동작한다. 그 호출 조건은 다음과 같다.

if (a != null && !more) {
    ...
    parent.finishAnimatingView(this, a);   // [글쓴이 주석] 목록에서 빼고 window 에서 분리
}

조건은 둘이다. 그리는 시점에 뷰가 애니메이션(a)을 갖고 있어야 하고, 그 애니메이션에 더 진행할 것이 없어야(!more) 한다. 이 조건이 애니메이션이 끝나는 순간에 어떻게 평가되는지 따라가 보자.

만료 프레임: 정리가 한 프레임 미뤄진다

애니메이션 시간이 다 된 프레임에서 Animation.getTransformation() 은 두 가지 일을 한다. 종료 리스너를 바로 부르지 않고 메인 스레드 큐의 맨 앞에 넣는다. 그리고 mOneMoreTime 플래그 때문에 true 를 한 번 더 돌려준다.[6]

if (expired) {
    ...
    fireAnimationEnd();      // [글쓴이 주석] handler 가 있으면 postAtFrontOfQueue(mOnEnd)
}
if (!mMore && mOneMoreTime) {
    mOneMoreTime = false;
    return true;
}
return mMore;

more 가 true 이면 parent 는 다시 그리기를 요청하므로, 끝 상태가 반영된 프레임이 한 번 더 그려진다. 그래서 이 프레임에서는 정리가 실행되지 않고, 정리는 다음 프레임으로 미뤄진다. 이때의 전제는 다음 프레임에도 뷰가 애니메이션을 갖고 있다는 것이다.

큐 맨 앞의 SDK 콜백

두 프레임 사이에, 큐 맨 앞에 넣어 둔 SDK 의 닫기 애니메이션 종료 콜백이 먼저 실행된다.

override fun onAnimationEnd(animation: Animation?) {
    inAppMessageView.clearAnimation()
    inAppMessageView.visibility = View.GONE
    closeInAppMessageView()
}

clearAnimation() 이 뷰의 애니메이션을 null 로 만든다. 뷰는 이미 parent 가 없어서 closeInAppMessageView() 안의 removeViewFromParent() 는 아무 일도 하지 않고, SDK 의 닫힘 처리만 한 번 더 일어난다. 재현 로그에서 Closing in-app message view 와 Resetting after in-app message close. 가 두 번씩 찍히는 이유다.

다음 프레임에서 getAnimation() 은 null 이다. a != null 이 거짓이므로 finishAnimatingView() 는 불리지 않는다. 이후 어떤 프레임에서도 이 조건은 다시 참이 되지 않는다. 남은 정리 경로는 parent 가 window 에서 분리되는 것뿐이고, 그것은 Activity 가 종료될 때다. 그때까지 dispatchDraw() 는 매 프레임 이 뷰를 그린다.

VKPROBE : t=3000ms parent=false attached=true vis=8 anim=false ... h=2 am=Matrix{...-168.9988...}
VKPROBE : t=3250ms parent=false attached=true vis=8 anim=false ... h=2 am=null
VKPROBE : t=4000ms parent=false attached=true vis=8 anim=false ... h=2 am=null   (이후 계속 같음)

vis=8 은 GONE 이다. 애니메이션은 사라졌고(anim=false), 다음 프레임부터는 이동값(am)도 지워졌다. 보이지 않아야 할 뷰가 그 자리에 그려지고 있다.

정상 경로는 왜 괜찮은가

여기서 질문을 하나 던져 보자. 자동 닫기만 있을 때도 SDK 의 onAnimationEnd 는 같은 순서로 실행되고, 거기서도 clearAnimation() 이 먼저다. 그런데 정상 경로에서는 왜 잔상이 남지 않을까. 표를 보기 전에 답을 한 번 예상해 보자.

답은 그 순간 뷰가 어느 목록에 있느냐다.

정상 일반 자식→ 애니메이션 부착→ 애니메이션 제거→ 분리됨
잔상 일반 자식→ 애니메이션 부착→ 정리 대기 진입→ 애니메이션 제거→ Activity 종료까지 잔상

정상 경로에서는 SDK 콜백이 애니메이션을 먼저 지우고 그 다음에 뷰를 뗀다. removeViewInternal() 이 애니메이션 없는 뷰를 보고 즉시 분리하므로 finishAnimatingView() 가 필요 없다. 잔상 경로에서는 즉시 닫기가 애니메이션이 붙은 채 먼저 뗐기 때문에 Activity 가 살아 있는 동안에는 finishAnimatingView() 만이 뷰를 정리할 수 있었고, SDK 콜백이 그 호출 조건을 지웠다.

잔상은 두 사건이 이 순서로 겹칠 때만 생긴다.
1. 닫기 애니메이션이 붙어 있는 동안 즉시 닫기가 뷰를 parent 에서 제거해, 뷰가 정리 대기 목록에 들어간다.
2. 다음 프레임의 finishAnimatingView() 보다 먼저 SDK 종료 콜백이 애니메이션을 지운다.
1이 없으면 SDK 종료 콜백이 뷰를 정리하고, 2가 없으면 다음 프레임에 finishAnimatingView() 가 정리한다.
6장 요약

정리 대기 목록의 뷰는 애니메이션이 끝나는 프레임 다음에 a != null && !more 일 때 정리된다. SDK 종료 콜백이 그 사이에 clearAnimation() 을 부르면 이 조건이 다시는 성립하지 않는다.

7. 같은 모델로 잔상의 모양 설명하기

스와이프로 재현한 잔상은 늘 위쪽이 잘린 채 상태바 근처에 붙어 있었고, 검색 탭으로 재현한 잔상은 원래 자리에 온전히 남아 있었다. 처음에는 닫기 애니메이션의 중간 프레임이 멈춘 것이라고 생각했지만, 프로브가 기록한 마지막 이동값(am)은 null 이었다. 모양을 가른 것은 제거되는 순간의 높이였다. parent 에서 제거된 뷰는 다시 layout 되지 않으므로, 잔상은 그 순간의 크기로 굳는다.

8. 수정: 제거하기 전에 애니메이션을 지운다

원인이 애니메이션이 붙은 채 제거하는 것이므로, 즉시 닫기가 뷰를 제거하기 직전에 정상 경로처럼 애니메이션을 먼저 지우면 된다. 그 지점은 앱이 이미 등록해 둔 IInAppMessageManagerListener.beforeInAppMessageViewClosed() 다. 4장의 close() 코드에서 보듯, SDK 는 animateOut 으로 분기하기 직전에 이 콜백(beforeClosed)을 부른다.[9]

override fun beforeInAppMessageViewClosed(inAppMessageView: View, inAppMessage: IInAppMessage) {
    if (isForceHiding) inAppMessage.animateOut = false

    // 애니메이션이 붙은 채 떼면 정리되지 않는 잔상으로 남는다.
    // 리스너를 먼저 떼지 않으면 clearAnimation() 이 SDK 닫기를 한 번 더 부른다.
    if (!inAppMessage.animateOut) {
        inAppMessageView.animation?.setAnimationListener(null)
        inAppMessageView.clearAnimation()
    }

    if (!isForceHiding) return
    // ... 강제 닫기 통지 (기존 로직)
}

두 즉시 닫기 경로가 모두 여기를 지난다. 스와이프는 SDK 가 animateOut = false 로 바꾼 뒤 들어오고, 검색 탭 강제 닫기는 첫 줄에서 animateOut = false 로 바뀐다. 그래서 강제 닫기의 animateOut 설정을 정리 코드 앞으로 옮겼다.

리스너를 먼저 해제하는 데에도 이유가 있다. clearAnimation() 은 Animation.detach() 를 부르고, 애니메이션이 시작됐고 아직 끝나지 않았으면 종료 콜백을 큐 맨 앞에 넣는다. 리스너가 붙어 있으면 이어서 SDK 의 onAnimationEnd 가 실행되어 닫기가 한 번 더 처리된다. 리스너를 먼저 해제해야 애니메이션만 지울 수 있다.

이렇게 하면 이어지는 closeInAppMessageView() 의 removeViewInternal() 이 애니메이션 없는 뷰를 보고 즉시 분리한다. 뷰는 정리 대기 목록을 거치지 않는다.

SDK 가 아니라 앱에서 막은 이유

근본적인 수정 위치는 SDK 의 close() 다. 하지만 앱은 SDK 코드를 고칠 수 없다. 최신 버전인 44.0.0 에는 Activity 전환용 가드와, 이미 정리된 wrapper 의 재정리를 건너뛰는 처리가 더해졌다. 그래서 닫힘 처리가 두 번 찍히는 로그는 달라질 수 있다. 하지만 즉시 닫기의 removeView 분기와 닫기 종료 콜백의 clearAnimation() 순서는 33.0.0 과 같다. 코드만 읽어 확인했고 44.0.0 을 실행해 보지는 않았다. 업그레이드만으로는 해결되지 않을 것으로 보고, 앱이 이미 가진 리스너에서 막았다. Braze 에는 같은 원인 분석과 SDK 쪽 수정안을 이슈로 제보했다.[10]

9. 검증과 남은 한계

단위 테스트는 InAppMessageBlockManagerTest 에 세 케이스를 더했다. 검색 탭 강제 닫기와 스와이프 닫기에서는 리스너 제거와 clearAnimation() 이 이 순서로 불리는지 확인한다. 애니메이션 닫기에서는 붙어 있는 애니메이션을 건드리지 않는지 확인한다. 수정 코드를 되돌리면 앞의 두 테스트가 실패하는 것도 확인했다.

다만 JVM 테스트는 mock 으로 호출 순서만 고정한다. 잔상은 실제 ViewGroup 과 프레임 위에서만 생기므로, 수정 빌드로 실기기(Galaxy S21 Ultra)에서 재현 조건을 다시 만들었다.

모든 회차에서 Closing in-app message view 와 Removed view 가 한 번씩만 찍혔고, 닫힌 뒤 뷰는 attached=false 였다. 대조군을 뺀 나머지는 수정 전에 잔상이 남던 조건이다.

한계

  • 200ms 빌드의 검색 탭 겹침은 1회만 확인했다. 3초 진단 빌드의 결과로 보완하지만 반복 횟수는 적다.
  • Pixel 10 재현과 Galaxy S25 Edge 의 증상은 사람이 직접 확인했고, 로그는 남기지 않았다.
  • 수정은 아직 배포 전이다. 운영에서 제보가 사라졌는지는 확인하지 못했다.
  • 애니메이션 없이 닫히는 모든 IAM 닫기에서 남아 있던 애니메이션을 지운다. 열림 애니메이션 도중 닫히면 열림 완료 콜백(자동 닫기 예약 등)도 실행되지 않는다. 동작이 바뀌는 지점이라 PR 에 함께 적었다.
  • Activity 가 pause 될 때 SDK 가 뷰를 제거하는 경로도 구조상 같은 위험이 있다. 홈 버튼으로 시험한 2회에서는 잔상이 남지 않았고, 더 파고들지 않았다.
  • 앱 쪽 우회다. SDK 가 고쳐지면 이 코드는 지울 수 있다.

10. 정리

  • 1애니메이션이 붙은 뷰를 제거하는 것 자체는 정상이다. 퇴장 애니메이션을 보여 주려는 Android 의 설계다. 문제는 그 뒤 finishAnimatingView() 가 불리기 전에 누군가 애니메이션을 지울 때 생긴다. 애니메이션 종료 콜백 안에서 지우는 것도 여기에 해당한다.
  • 2애니메이션 없이 즉시 제거하려는 경로라면 먼저 애니메이션을 지운다. 리스너까지 해제할지는 그 종료 콜백에 꼭 필요한 처리가 있는지 보고 정한다. 이번에는 SDK 의 닫기 콜백이 중복이라 해제했다.
  • 3보이는데 view tree 와 터치 대상에 없다면 mDisappearingChildren 을 의심한다. parent == null 이면서 isAttachedToWindow == true 인 상태는 정상 퇴장 중에도 잠깐 나타난다. getAnimation() == null 인 채로 이 상태가 계속되면 정리되지 않은 뷰다.
  • 4타이밍 버그는 창을 넓혀 결정적으로 만든다. 애니메이션 길이처럼 순서를 바꾸지 않는 값을 늘리면 사람이 재현하고 관찰할 수 있다.

removeView() 는 뷰를 parent 에서 제거하는 함수가 맞다. 다만 애니메이션이 붙어 있으면 분리를 애니메이션이 끝난 뒤로 미루고, 그 정리는 다음 프레임에도 애니메이션이 남아 있어야 실행된다. 코드베이스에서 애니메이션 종료 콜백과 즉시 제거가 서로 다른 경로로 같은 뷰를 다루는 곳을 한 번 찾아보자.
