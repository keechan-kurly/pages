536,760 bytes — 스택트레이스가 가리킨 곳

Crashlytics에 낯선 크래시가 올라왔다. 메시지는 이랬다.

java.lang.RuntimeException: android.os.TransactionTooLargeException:
    data parcel size 536760 bytes
    ...
    at android.app.servertransaction.PendingTransactionActions$StopInfo.run(...)
Caused by: android.os.TransactionTooLargeException: data parcel size 536760 bytes
    at android.os.BinderProxy.transactNative(Native Method)
    at android.app.IActivityClientController$Stub$Proxy.activityStopped(...)

두 가지가 눈에 띈다. 하나는 536,760 bytes(약 524KB)라는 숫자. 다른 하나는 크래시가 터진 지점이 activityStopped라는 것. 사용자 입력이나 렌더링이 아니라, 액티비티가 화면에서 가려지며 상태를 저장하는 경로에서 죽었다.

여기서 한 가지 짚고 넘어가자. activityStopped(즉 onStop)는 "백그라운드로 내려갈 때"만 발생하지 않는다. 다른 액티비티로 이동해 현재 화면이 가려질 때(A→B)도 똑같이 stop된다. 홈 셸인 MainActivity는 상품상세·장바구니·카테고리로 이동할 때 늘 stop되므로, 오히려 이쪽이 더 잦은 트리거일 수 있다. 스택트레이스만으로는 둘을 구분할 수 없다. 다만 어느 경로든 공통점은 하나다 — 시스템이 "이 액티비티가 죽을 수 있으니 상태를 저장해 두자"며 상태 저장을 트리거했다는 것. 이게 이번 크래시가 입력·렌더링 문제가 아니라 저장되는 Bundle의 크기 문제라는 첫 단서다.

안드로이드는 액티비티가 멈출 때 onSaveInstanceState로 화면 상태를 Bundle에 담아 시스템 프로세스로 전달한다. 이 전달은 Binder 트랜잭션을 타는데, Binder에는 프로세스 전체가 공유하는 약 1MB 버퍼가 있고 단일 트랜잭션은 실무상 512KB 부근에서 한계에 부딪힌다.[1] 우리가 저장하려던 Bundle이 그 선을 넘은 것이다. 그리고 근본 원인이 Bundle 크기인 이상, 이 크래시는 트리거(백그라운드든 화면 이동이든)와 무관하게 재현된다.

다행히 이 크래시 로그에는 시스템이 친절하게 붙여 준 Bundle stats가 딸려 있었다. 어떤 키가 몇 바이트를 먹었는지 트리로 찍힌다. 재현 기기도, 힙 덤프도 없이 이 트리 하나만으로 근본 원인까지 내려가 보기로 했다.

이 글에서 도착할 곳
  1. 스택트레이스의 Bundle stats를 해부해 범인을 특정한다.
  2. "왜 이 버전부터 터지는가"를 밝힌다.
  3. 크래시가 나기 전에 크래시 Bundle을 재현하는 계층 로거로 가설을 하나씩 실측 소거한다.
  4. 저장 위치를 바꾸는 우회책이 아니라 대용량을 Bundle에 아예 싣지 않는 근본 수정으로 536KB를 49KB까지 줄인다.

Bundle stats 해부 — 416KB의 정체는 viewPager였다

로그의 Bundle stats를 위에서부터 따라 내려가면 무게가 어디에 쏠려 있는지 금방 드러난다. 크기 순으로 가지치기하면 이렇다.

total 536,760 └ android:support:fragments 527,204 └ fragment_b673… (HomeRootFragment) 526,780 ├ viewState │ └ 0x7f0a07db 416,048 ← ? └ childFragmentManager 106,808 ├ fragment_a20d… (HomeRecommendation) 5,480 └ fragment_c44a… 100,648 └ … └ arguments / productListInfo 47,672 └ registryState / … / productListInfo 47,672

지배적인 두 덩어리가 보인다. 하나는 viewState 안의 0x7f0a07db가 혼자 먹는 416KB. 다른 하나는 childFragmentManager 깊숙한 곳에서 productListInfo라는 값이 47KB씩 두 번 나타나는 것.

먼저 0x7f0a07db. 이건 리소스 ID의 16진수 값이다. 빌드 산출물의 R.txt에서 바로 역참조할 수 있다.

# app/build/intermediates/runtime_symbol_list/.../R.txt
int id bottom_navigation 0x7f0a00db
int id viewPager         0x7f0a07db   ← 416KB의 정체

0x7f0a07db = R.id.viewPager. 홈 루트 화면(HomeRootFragment)의 ViewPager가 저장하는 상태만 416KB였다. 나머지 47KB×2는 그 안 어딘가의 상품 목록 데이터. 두 실마리를 각각 끝까지 따라가면 된다.

왜 하필 3.78.0인가

여기서 중요한 제약이 하나 걸렸다. 이 크래시는 특정 버전(3.78.0)부터 관측됐다. 오래 잠복해 있던 문제가 아니라 회귀라는 뜻이다. 그렇다면 원인은 "누적된 구조"가 아니라 "그 버전에서 바뀐 무언가"다. git log로 홈 관련 파일들의 변경을 훑었다.

홈 루트는 여러 개의 서브탭을 ViewPager + FragmentStatePagerAdapter로 붙인다. 탭 종류는 서버 설정으로 내려온다 — 추천, 컬렉션, 컬렉션그룹, 카테고리, 이벤트 등. 문제의 버전에 들어간 커밋 하나가 이 중 컬렉션그룹 탭을 XML 기반에서 Compose 기반으로 전환하면서 내부 구조를 바꿔 놓았다.

3.77 이전 — 컬렉션그룹 탭
class HomeCollectionGroupFragment :
    BaseFragment(...) {
  // RecyclerView + Mediator 로
  // 목록을 직접 그림.
  // 자식 Fragment 없음 → light
}
3.78.0 이후
class HomeCollectionGroupFragment :
    Fragment(...) {
  // ComposeView + 자식
  // ProductListFragment 호스팅
  // → 47KB 페이로드 탑재 → heavy
}

전환 자체는 정상적인 마이그레이션이다. 문제는 부수 효과였다. 자식 ProductListFragment는 예전부터 자신의 arguments에 상품 목록 정보(ProductListInfoUIModel)를 담아 왔는데, 이 객체가 배너·정렬·필터·섹션 리스트에 상위 카테고리까지 재귀로 안고 있어 직렬화하면 수십 KB에 이른다.

정리하면 이렇다. 컬렉션·카테고리 탭은 이전부터 이 무거운 자식을 안고 있었다(heavy). 컬렉션그룹 탭만 예외적으로 RecyclerView라 가벼웠는데(light), 3.78.0이 이걸 heavy로 바꿨다. 문제의 사용자 화면은 컬렉션그룹 탭이 여러 개인 구성이었다.

3.78.0의 회귀는 "탭 하나가 더 무거워진 것"이 아니라 "무거운 탭의 개수가 늘어난 것"이었다. 그리고 FragmentStatePagerAdapter는 스쳐 간 탭들의 상태를 누적한다.

진짜 범인 — 47KB가 두 번 저장되고 있었다

이제 두 실마리가 하나로 합쳐진다. 왜 productListInfo가 두 번 저장되고, 왜 viewPager 상태가 416KB까지 부풀었는가.

productListInfo가 저장되는 두 곳 — arguments, 그리고 아무도 쓰지 않는 SavedStateHandle

첫 번째 사본은 명백하다. ProductListFragment를 만들 때 47KB 객체를 arguments 번들에 넣는다. 두 번째 사본이 함정이었다. 로그에는 같은 값이 ViewModel의 SavedStateHandle 아래에도 47KB로 찍혀 있었다.

// 저장되는 Bundle 트리 — 같은 값이 두 곳에
arguments / productListInfo                          47,672
registryState / … / SavedStateHandlesProvider /
    VIEW_MODEL_KEY_PRODUCT_FILTER / productListInfo   47,672

그런데 코드베이스 어디에도 savedStateHandle["productListInfo"] = ...로 이 값을 직접 쓰는 곳이 없었다(grep으로 확인). 그렇다면 이 사본은 어디서 왔는가?

Hilt로 만든 ViewModel의 SavedStateHandle은 소유 Fragment의 arguments를 기본값으로 자동 시딩한다. 그리고 프로세스 사후 복원을 대비해, 자신이 들고 있는 모든 키를 저장 시점에 다시 직렬화한다.

즉 arguments에 47KB를 넣는 순간, 프레임워크가 그 값을 SavedStateHandle로 복사하고, 저장 때 한 번 더 직렬화한다. 아무도 명시적으로 쓰지 않았는데도 47KB × 2가 된다. 이 프로젝트에서는 그 값을 SavedStateHandle에서 읽지도 않으니, 두 번째 사본은 순수한 잉여였다.[2]

416KB — 파괴된 탭들의 누적

남은 416KB, 즉 viewPager 상태를 보자. FragmentStatePagerAdapter는 화면 밖으로 밀려난 오프스크린 페이지의 Fragment 인스턴스는 파괴하지만, 돌아왔을 때 복원하려고 그 상태 스냅샷은 내부 리스트에 보관한다. 이 리스트는 트리밍되지 않는다 — 방문했던 모든 위치의 스냅샷이 쌓인다.[3]

한 탭의 스냅샷에는 그 탭의 childFragmentManager, 곧 중첩된 ProductListFragment의 47KB×2가 통째로 들어간다. 사용자가 무거운 탭들을 스와이프하며 지나갈수록 스냅샷이 누적된다. 방문한 heavy 탭 수 × ~95KB가 이 416KB의 실체다.

크래시의 전체 공식
total =

+

살아있는 탭은 offscreenPageLimit(현재 ±1)로 3개에 묶여 유한하다. 한도를 넘기는 변수는 누적되는 viewPager(파괴된 탭) 쪽이다. 그리고 각 탭이 무거운 이유는 47KB가 두 번 저장되기 때문이다.

추론을 멈추고 측정하기 — 계층 로거

여기까지는 로그 한 장에서 짜낸 추론이다. 그럴듯하지만 검증되지 않았다. 재현 기기의 탭 구성도 모르고, "무거운 탭 5개 × 95KB"라는 산수도 가정이다. 추론을 더 쌓는 대신, 측정 도구를 만들기로 했다.

아이디어는 단순하다. 시스템이 크래시 때 찍어 준 Bundle stats 트리를, 크래시가 나기 전에 우리 손으로 재현하는 것. onSaveInstanceState가 채운 outState를 재귀 순회하며 각 노드를 Parcel에 써서 실제 직렬화 크기를 잰다.

object SavedStateSizeLogger {
    fun sizeOf(value: Any?): Int {
        val parcel = Parcel.obtain()
        return try {
            parcel.writeValue(value)
            parcel.dataSize        // 실제 parcel 바이트
        } finally { parcel.recycle() }
    }
    // Bundle 은 재귀, SparseArray(viewState)도 재귀,
    // fragment_<uuid> 키엔 FragmentManager 트리에서 찾은 클래스명 병기
}

여기에 작은 디테일 하나를 더했다. Bundle 트리의 fragment_<uuid> 키는 UUID라 어떤 화면인지 알 수 없다. 그래서 FragmentManager 트리를 함께 순회해 uuid → 클래스명 맵을 만들고 로그에 병기했다. 이제 트리를 읽으면 어느 노드가 HomeCollectionGroupFragment이고 어느 게 중첩 ProductListFragment인지 눈으로 바로 잡힌다.

이 로거를 MainActivity.onSaveInstanceState의 super 호출 직후(디버그 빌드에서만) 한 줄 붙이고, 실기기에서 탭을 스와이프한 뒤 백그라운드로 보냈다. 크래시 로그와 같은 포맷의 트리가, 이번엔 크래시 없이 손에 들어왔다.

디버깅에서 가장 비싼 건 코드 수정이 아니라 "어디가 문제인지 확신하는 일"이다. 재현되는 측정값 한 번이 그럴듯한 추론 다섯 개를 이긴다.

근본 수정 — 대용량을 Bundle에 싣지 않는다

돌파구는 ProductListFragment가 그 47KB를 실제로 어떻게 쓰는지 확인하면서 열렸다. ViewModel은 init에서 넘겨받은 거대 객체를 그대로 쓰지 않고, 안에서 GetCurrentProductListInfoUseCase로 서버에서 다시 조회하고 있었다. 그 UseCase가 요구하는 입력은 이게 전부였다.

data class Param(
    val type: ProductListPageType,   // enum
    val site: SiteFilterType,        // enum
    val code: String,
    val title: String? = null,
    val parentCode: String? = null,
    // ...
)

즉 47KB 객체는 type·code·title·parentCode·brandId 같은 primitive 몇 개를 추출하는 용도로만 소비됐고, 실제 목록 데이터(필터·배너·섹션)는 어차피 code로 서버에서 다시 만들어졌다. Bundle을 건너온 47KB의 99%는 도착하자마자 버려지고 있었던 것이다.

그렇다면 답은 자명하다. 47KB 객체 대신 primitive만 넘긴다.

Before — 47KB Parcelable
fun create(
  productListInfo: ProductListInfoUIModel?,
  site: SiteFilterType,
) = ProductListFragment().apply {
  arguments = Bundle().apply {
    putParcelable(
      KEY, productListInfo)  // 47KB
  }
}
After — primitive만
fun create(
  type: ProductListPageType,
  site: SiteFilterType,
  code: String,
  groupCode: String? = null,
  /* title, brandId ... */
) = ProductListFragment().apply {
  arguments = bundleOf(...)  // 수백 B
}

기존 동작을 지키기 위해, ViewModel의 실제 로직은 primitive를 받는 init으로 옮기고, 기존 init(uiModel)은 그 uiModel에서 primitive만 뽑아 위임하는 얇은 오버로드로 남겼다. 기존 단위 테스트는 이 위임 경로를 그대로 타므로 손대지 않고 통과했다 — 위임 자체가 "uiModel에서 실제로 쓰이던 건 primitive뿐"이라는 동치성의 증거이기도 하다.

중요한 부수 효과 하나. arguments에서 47KB를 빼면, 거기서 자동 시딩되던 SavedStateHandle 사본도 함께 사라진다. 두 사본(arguments · SavedStateHandle)이 한 번에 제거된다.

536KB → 49KB, 그리고 남는 것

같은 내비게이션을 두 빌드에서 반복하고 계층 로거로 총량을 찍었다. 판정은 명료했다.

항목수정 전primitive 수정 후변화
onSaveInstanceState 총량522,620 B (크래시)50,176 B-90%
viewPager 누적 blob308 KB15.5 KB-95%
childFragmentManager (살아있는 3탭)200 KB19 KB-90%
ProductListFragment / 탭95 KB2.9 KB-97%
arguments / SavedStateHandle의 productListInfo47 KB × 2사라짐제거

로그의 두 productListInfo 항목은 흔적도 없이 사라졌고, 각 탭은 95KB에서 2.9KB로 내려앉았다. 한도(약 512KB)의 10% 미만을 쓰며, 이제 탭을 아무리 스와이프해도 저장 위치가 아니라 저장량 자체가 작아졌으니 내비게이션과 무관하게 안전하다.

돌아보면 이 문제는 세 겹이었다. 표면은 Binder 한도 초과, 중간은 마이그레이션이 탭을 무겁게 만든 회귀, 바닥은 "서버에서 다시 받을 수 있는 데이터를 Bundle에 실어 나른" 설계였다. 저장 위치를 바꾸거나 저장을 막는 수정은 표면·중간만 건드릴 뿐, 바닥을 그대로 두면 문제는 다시 자란다.

남는 것
  • 저장 위치가 아니라 저장 여부. TransactionTooLargeException은 "무엇을 어디에 두느냐"가 아니라 "Bundle에 대용량을 싣느냐"의 문제다. 재조회 가능한 데이터는 키만 넘기고 다시 받는다.
  • arguments는 곧 SavedStateHandle이다. Fragment arguments에 넣은 값은 Hilt ViewModel의 SavedStateHandle로 자동 시딩되어 한 번 더 저장된다. 대용량 Parcelable을 arguments에 넣는 순간 비용은 두 배가 된다.
  • 추론 대신 측정. 크래시 Bundle 트리를 크래시 전에 재현하는 로거 한 개가, 그럴듯한 수정안들을 말이 아니라 로그로 빠르게 판정하게 해 줬다.

마지막으로, 같은 함정을 팀 코드에서 미리 잡고 싶다면 확인할 지점은 좁다. Fragment arguments에 들어가는 Parcelable이 서버 응답에서 다시 만들 수 있는 것인지만 물으면 된다. 답이 "그렇다"면, 그건 arguments가 아니라 code 한 줄로 충분하다.
