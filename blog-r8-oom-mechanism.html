어느 JVM이 죽었는가 — R8 OutOfMemoryError의 메커니즘

Gradle Daemon, Worker API, 그리고 whole-program optimizer의 메모리

R8 Gradle JVM AGP Build
관찰된 두 메시지

CI (Linux): R8: java.lang.OutOfMemoryError: Java heap space

Local (macOS): Gradle build daemon stopped: garbage collector is thrashing

두 줄의 단서

매주 일요일 새벽, develop 브랜치에서 도는 Weekly Baseline Profile PR 워크플로가 13분간 빌드를 돌린 끝에 같은 자리에서 죽었다. 실패 지점은 :app:minifyStoreBenchmarkReleaseWithR8 단계. CI 로그의 마지막 줄은 다음과 같았다.

ERROR: R8: java.lang.OutOfMemoryError: Java heap space
> Task :app:minifyStoreBenchmarkReleaseWithR8 FAILED

같은 명령을 로컬 macOS에서 동일한 JVM 인자(-Xmx4g -XX:MaxMetaspaceSize=1g)로 재현했더니 이번에는 다른 메시지가 나왔다.

The Daemon will expire immediately since the JVM garbage collector is thrashing.
The currently configured max heap space is '4 GiB' and the configured max metaspace is '1 GiB'.

FAILURE: Build failed with an exception.
* What went wrong:
Gradle build daemon has been stopped: since the JVM garbage collector is thrashing

같은 task, 같은 옵션, 같은 R8 단계인데 한쪽은 Java heap space로, 다른 한쪽은 garbage collector is thrashing으로 죽었다. 두 메시지는 다른 단계에서 나온 다른 에러처럼 보인다. 그러나 결론부터 말하면 이는 같은 사건의 두 측면이다.

이 글은 그 두 측면을 추적한다. 먼저 JVM 메모리 구조에서 두 메시지가 어떻게 갈라지는지 살펴보고, "어느 JVM의 heap이 죽었는가"라는 본질 질문으로 들어간다. 그 답을 찾고 나면 마지막 질문이 남는다 — 왜 R8은 그 정도의 heap을 요구하는가. 처방은 글의 끝에 한 단락으로 정리한다.

두 메시지가 다른 이유

JVM Heap과 Gradle의 자기보호

R8 OOM을 진단하려면 JVM 메모리 모델의 두 영역부터 짚어야 한다. Heap과 Metaspace는 별개의 영역이다. 객체(클래스 인스턴스)는 heap에 할당되고, 클래스 자체의 메타데이터(메서드 테이블, 상수 풀, 어노테이션)는 metaspace에 적재된다. JDK 8 이전엔 두 영역이 PermGen으로 묶여 있었지만, 이후 분리되어 각자 독립된 한도를 가진다[1].

우리 워크플로 명령에 등장한 두 옵션이 정확히 이 분리에 대응한다.

# Heap 의 최대 크기 (4 GiB)
-Xmx4g

# Metaspace 의 최대 크기 (1 GiB)
-XX:MaxMetaspaceSize=1g

R8의 OOM은 거의 항상 Heap 부족이다. R8이 만들어내는 것은 클래스 메타데이터가 아니라 그 클래스들 사이의 reference graph 같은 분석 객체이기 때문이다. 이 점을 짚고 나면 두 메시지의 차이를 풀 준비가 된다.

java.lang.OutOfMemoryError: Java heap space는 JVM 표준 예외다. JVM이 새 객체를 heap에 할당하려는데 free 영역이 없고 GC로도 회수가 불가능할 때, 해당 스레드에 throw한다. CI 로그의 R8: prefix는 R8이 자신의 작업 스레드에서 catch해 자기 로그 형식으로 다시 출력한 흔적이다. 결국 R8 worker 스레드가 객체 할당 중 직접 OOM을 받았다는 뜻이다.

로컬에서 본 "garbage collector is thrashing"은 JVM 예외가 아니라 Gradle의 자기보호 메시지다. Gradle Daemon은 자체적으로 GC 시간을 모니터링한다. JVM이 실제 OOM을 throw하기 전 단계, 즉 GC가 거의 시간을 다 차지하면서 회수량이 적은 상태(이를 GC thrashing이라 부른다)가 임계 시간 이상 지속되면, Gradle은 그 daemon을 자발적으로 만료시킨다. 다음 빌드를 위해 깨끗한 daemon을 새로 띄우려는 의도다. 사용자에게는 빌드 실패로 보이지만, JVM 입장에선 아직 OOM이 throw되기 전 시점에 종료된 상태다.

두 메시지는 결국 이렇게 정리된다.

신호누가 띄웠나임계 시점
OutOfMemoryError: Java heap space JVM 객체 할당 실패 시점
daemon stopped: GC thrashing Gradle 객체 할당 실패 직전, GC 시간 비율 임계 초과

같은 압박이 누적되다가 JVM이 먼저 폭발하느냐, Gradle이 한발 먼저 daemon을 정리하느냐의 차이일 뿐이다. 본질은 같은 heap 부족이다.

-Xmx4g가 누구의 heap이었는가

이제 본질 질문으로 들어간다. 우리가 명령줄에 적은 -Dorg.gradle.jvmargs="-Xmx4g..."는 정확히 어느 JVM의 heap 한도였는가.

Gradle 공식 문서는 이 속성을 한 줄로 정의한다.

Specifies the JVM arguments used for the Gradle Daemon. ... This does not affect the JVM settings for the Gradle client VM.

— docs.gradle.org, The Build Environment[2]

즉 -Xmx4g는 Gradle Daemon JVM의 heap이다. CLI를 띄운 client VM은 아니다. 그렇다면 다음 질문은, R8은 그 daemon JVM 위에서 도는가 아니면 별도 프로세스에서 도는가 — 이다.

R8은 Gradle Worker API를 통해 호출되는 worker action이다. Worker API는 세 가지 격리 수준을 제공한다[3].

Isolation메모리 공유
No isolation부모 JVM의 classloader/heap 직접 공유
ClassLoader isolation같은 JVM, classloader만 격리
Process isolation별도 JVM 프로세스, heap 완전 분리

AGP 8.x는 R8을 별도 프로세스로 띄우는 방법을 명시적인 opt-in으로 제공한다. settings.gradle에서 R8 Execution Profile을 정의하고 runInSeparateProcess = true를 주는 방식이다[4].

android {
    execution {
        profiles {
            create("server") {
                r8 {
                    runInSeparateProcess = true
                    jvmOptions += listOf(
                        "-Xms2048m",
                        "-Xmx8192m",
                        "-XX:+HeapDumpOnOutOfMemoryError",
                    )
                }
            }
            defaultProfile = "server"
        }
    }
}

이 옵션이 opt-in이라는 점이 핵심이다. settings.gradle에 위 블록이 없으면 R8 worker는 별도 프로세스에서 돌지 않는다. 즉 Gradle Daemon JVM 안에서 worker로 동작하며, daemon의 heap을 그대로 공유한다. 우리 프로젝트의 settings.gradle에는 이 블록이 없다. 따라서 우리 -Xmx4g는 Gradle Daemon JVM의 heap = R8 worker가 작업한 heap이었다.

여기에 --no-daemon이라는 추가 변수가 있다. 이 옵션은 daemon을 띄우지 않는 것이 아니라, single-use daemon을 fork해 빌드 1회만 사용하고 종료한다. 결과적으로 매 빌드가 cold JVM 위에서 시작된다. JIT 캐시 없이 인터프리터 모드로 출발해 바이트코드 실행 중 점진적으로 컴파일하므로, 같은 R8 작업이라도 GC 빈도와 메모리 working set이 daemon 재사용 케이스보다 두꺼워진다. 우리 워크플로의 두 단계 모두 --no-daemon이 붙어 있다.

정리하면 우리 -Xmx4g는 다음 모든 부담을 떠안고 있는 JVM의 heap이었다.

  • Gradle Daemon 자체 (Configuration phase, task graph, build cache 인메모리 인덱스)
  • AGP의 R8Task 코드
  • R8 worker가 만들어내는 분석 객체 — reference graph, IR, 매핑 테이블
  • JIT 컴파일러가 점진적으로 따뜻해지면서 늘어나는 워킹 셋

이제 마지막 변수 하나만 남았다. 저 R8 worker가 정확히 얼마나 메모리를 요구하는가, 그리고 왜 그런가.

R8이 메모리를 먹는 진짜 이유

whole-program reference graph

R8 자체의 정의는 단순하다.

R8 is a java program shrinking and minification tool that converts java byte code to optimized dex code.

— r8.googlesource.com, R8 README[5]

여기서 메모리 부하를 결정하는 단어가 whole-program이다. R8은 모듈 단위 컴파일러가 아니라 앱 전체를 하나의 단위로 분석하는 whole-program optimizer다. 이는 구체적으로 다음을 의미한다 — R8이 동작하는 동안, 앱과 모든 의존성의 클래스 그래프가 동시에 메모리에 적재되어 있어야 한다. 메모리 곡선이 코드량(MB)에 선형이 아니라 참조 밀도(reference density)에 비례해 비선형으로 늘어나는 근본 이유가 여기에 있다.

R8의 동작은 공식 문서 기준 네 단계로 나뉜다[6].

1단계 — Code Shrinking (tree shaking)

R8의 첫 작업이자 메모리 부담이 가장 큰 단계다.

R8 identifies and removes unreachable code from your application and its library dependencies. By analyzing the entry points of your app (such as Activities or Services defined in the manifest), R8 builds a graph of referenced code and removes anything that remains unreferenced.

— developer.android.com, Shrink, obfuscate, and optimize your app

핵심 동사는 builds a graph다. R8은 manifest의 component, ProGuard keep rules 등을 entry point로 삼아, 그 지점에서 reachable한 모든 클래스/메서드/필드를 그래프로 구축한다. 이 그래프는 앱 코드뿐 아니라 모든 의존성 jar의 클래스를 노드로 갖는다. 노드 수십만 개, 엣지 수백만 개의 데이터 구조가 한꺼번에 heap에 펼쳐진다는 뜻이다.

2단계 — Logical Optimizations

그래프를 갖고 다음 두 종류의 변환을 수행한다.

Method Inlining: R8 replaces a method call site with the actual body of the called method... Class Merging: R8 combines sets of classes and interfaces into a single class.

— 위 문서

각 변환 후보를 평가하려면 호출 그래프의 양 끝(call site, callee body)을 동시에 메모리에 두고 IR(중간 표현)로 변환해 비교해야 한다. Inlining 후보, class merge 후보 정보가 누적되며 IR이 메모리에 쌓인다.

3단계 — Obfuscation

모든 식별자에 새 이름을 부여하고 그 매핑을 mapping.txt로 기록한다.

R8 shortens the names of classes, fields, and methods (for example, com.example.MyActivity could become a.b.a).

매핑 테이블 자체는 비교적 작지만, 1~2단계 산출물 위에 추가되는 자료구조다.

4단계 — DEX 작성

최종 dex 바이트코드를 메모리 버퍼에 작성한 뒤 디스크로 flush한다.

여기에 한 가지 변수가 더 있다. AGP 8.0 이상에서 기본 활성화된 R8 Full Mode다.

R8 full mode provides significantly more powerful optimization. It is enabled by default.

— developer.android.com, Shrink, obfuscate, and optimize your app

Full Mode는 더 공격적인 가정을 채택한다. 예컨대 keep rule로 명시되지 않은 missing class는 의도된 것으로 간주하고 더 깊은 inlining/merging을 시도한다. 결과적으로 분석 그래프와 IR이 더 두껍게 쌓이며, 같은 입력 대비 메모리 점유가 늘어난다. AGP 8.0 이상을 사용한다면 이 모드가 기본값이라는 점을 인지하고 있어야 한다.

네 단계를 합쳐 메모리 곡선을 그리면 대략 이런 형태다.

1~2단계 사이가 가장 두껍다. tree shaking의 reference graph가 아직 메모리에 남아 있는데 logical optimization의 IR이 그 위에 쌓이기 때문이다. CI 로그의 OOM 시점도 이 구간일 가능성이 높다.

이 구조에서 4 GiB가 부족했던 이유는 명료하다 — 우리 앱은 40개 이상의 자체 모듈 + 수백 개의 의존성 jar를 갖는다. 그 모두의 클래스가 노드가 되는 reference graph + IR + R8 외 Gradle/AGP 자체의 워킹 셋이 한 heap 안에서 경쟁한다. 4 GiB는 그 경쟁에서 R8이 자기 분석 객체를 다 펼치기 직전 한도와 위태롭게 맞물려 있던 수치다.

왜 평소엔 통과하던 빌드가 이번엔 죽었는가

같은 워크플로가 한동안 통과해 왔다는 사실은 이 분석에 반론처럼 작동한다. 4 GiB가 본질적으로 부족하다면 매번 죽어야 하지 않는가. 답은 두 가지 외부 변수가 이번 실행에서 동시에 깨졌기 때문이다.

첫째, GitHub Actions cache의 광범위한 미스. 이번 실행의 워크플로 annotation에는 다수의 캐시 키가 Cache service responded with 400으로 실패한 기록이 있다.

Failed to restore gradle-home-v1|Linux|generate-baseline-profile[...]:
  Error: Cache service responded with 400
Failed to save cache entry with path
  '/opt/.../.gradle/caches/transforms-4/*/...'

영향을 받은 키는 dependency cache, transforms cache, kotlin-dsl accessor cache, gradle wrapper cache 등 빌드 핵심 경로 거의 전체였다. 결과적으로 이번 빌드는 의존성 해상도, AGP transform, kotlin-dsl 컴파일을 cold 상태에서 처음부터 수행했다. 이는 R8 단계와 직접 인과는 없지만 같은 daemon JVM의 working set을 평소보다 두껍게 만든다. R8 worker가 자기 분석 객체를 펼칠 즈음, 그 옆 자리는 평소보다 좁아져 있었다.

둘째, --no-daemon 누적 효과. 앞서 본 대로 우리 명령은 daemon 재사용을 포기한다. JIT가 따뜻해지지 않은 상태에서 인터프리터 실행이 길어지면 같은 객체 생성률에서도 minor GC가 더 자주 발생하고, tenured 영역으로 promotion되기 전 객체가 일시적으로 누적되며 heap pressure가 올라간다. cold start와 cache miss가 겹치면 이 효과가 가산된다.

평소엔 이 두 조건 중 하나가 살아 있어 4 GiB 안에 R8이 들어왔던 것이다. 이번엔 둘 다 깨지면서 reference graph 구축 단계에서 정확히 한도에 부딪혔다. 즉 4 GiB는 외부 조건이 우호적일 때만 통과 가능한 수치였고, 빌드는 점점 그 가장자리를 향해 자라고 있었다.

처방

원리를 알면 처방은 비교적 단순해진다. 두 갈래가 있다.

처방변경 위치효과단점
Daemon -Xmx 상향 (4g → 8g) *.yml 즉효, 1줄 변경 Daemon 전체에 큰 heap을 항상 잡음. CI runner RAM 압박
R8 Execution Profile 분리 (runInSeparateProcess) settings.gradle R8만 격리된 JVM에서 동작, daemon 영향 없음 AGP 8.x 이상 필요, 설정 추가

전자는 같은 heap 안에 모든 부담을 그대로 두고 한도만 늘리는 방식이고, 후자는 heap을 둘로 나눠 R8만 자기 공간에서 일하게 하는 방식이다. 단기 처방으로는 전자가, 빌드 인프라 정합성으로는 후자가 옳다. 우리 팀의 1차 처방은 워크플로의 -Xmx4g를 이미 통과 중인 빌드 단계와 동일한 -Xmx8g로 맞추는 변경이다. R8 Execution Profile 분리는 후속 과제로 남는다.

정리

두 줄의 단서로 시작했다. CI의 Java heap space와 로컬의 garbage collector is thrashing은 다른 사건이 아니라 같은 heap의 두 측면이었다. 먼저 JVM 메모리 구조에서 두 진단이 어떻게 갈라지는지 보았고, -Xmx4g가 Gradle Daemon JVM의 heap이며 R8 worker가 별도 프로세스가 아닌 그 daemon 안에서 동작한다는 사실을 확인했다. 그 다음 R8이 whole-program optimizer라는 본질에서 reference graph가 메모리를 비선형으로 차지하는 이유를 짚었다. 마지막으로 cache miss와 --no-daemon이 평소엔 살아 있던 안전 마진을 깎아내며 4 GiB 한도를 건드렸음을 보았다.

Takeaway

R8 OOM은 R8의 결함이 아니다. whole-program optimizer라는 본질과 Gradle Daemon JVM과 heap을 공유하는 구조가 만나는 자리에서 자연스레 발생하는 압박이다.

다음에 같은 메시지를 만나면 두 질문을 먼저 던지자. 어느 JVM의 heap이 죽었는가, 그리고 어느 단계에서 죽었는가. 이 두 답이 처방의 절반을 이미 결정한다.
