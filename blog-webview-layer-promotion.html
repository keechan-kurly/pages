NONE으로 막았던 크래시가 돌아왔다

1편에서 우리는 상품설명 WebView의 레이어 타입을 LAYER_TYPE_NONE으로 바꿔 크래시를 막았다고 썼다. 하드웨어 레이어를 쓰지 않으면 WebView 크기만 한 텍스처를 만들 일도 없다는 논리였다. 그리고 몇 달 뒤, 같은 메시지가 다시 쌓이기 시작했다.

Caused by: java.lang.IllegalStateException:
  Unable to create layer for WebView, size 1088x16384 max size 16383 color type 4 has context 1

숫자까지 1편과 똑같았다. 높이 16384, 한도 16383, 차이는 1px이다. 그런데 이번에는 코드 어디에도 LAYER_TYPE_HARDWARE가 없었다. 크래시는 최신 릴리즈 전반에서 하루 몇 건씩 꾸준히 쌓였고, 전부 삼성 단말, 전부 Android 12 이상이었다.

결론부터 말하면 LAYER_TYPE_NONE은 "레이어를 쓰지 않는다"는 뜻이 아니었다. 이 글은 다음 네 가지를 차례로 다룬다.

  • 1레이어를 요청하지 않아도 렌더러(hwui)가 View를 레이어로 올리는 자동 승격
  • 2Android 12 stretch overscroll이 WebView 자신을 승격시키는 경로
  • 3크기 검사(16383)와 할당(16384)이 어긋나는 hwui의 경계
  • 4한 줄 수정과 실기기 검증
1편 다시 보기

GPU 최대 텍스처 크기(maxTextureSize)가 64의 배수가 아닌 단말(16383)에서, 레이어 높이가 64의 배수로 올림되며 16384가 되어 할당에 실패했다. 당시 대응은 레이어 타입을 LAYER_TYPE_HARDWARE에서 LAYER_TYPE_NONE으로 바꾸는 것이었다.
→ 1px이 앱을 죽였다

단서: 메시지가 가리킨 노드

스택은 Chromium 쪽 문제처럼 보였다. 최상단 프레임이 org.chromium.base.JniAndroid.handleException이고, 그 아래로 WebView APK의 네이티브 주소가 이어지다 libhwui.so에서 끝난다. 하지만 메시지 문구는 Chromium이 아니라 Android 렌더러인 hwui 소스에 있다.

// libs/hwui/pipeline/skia/SkiaGpuPipeline.cpp, createOrUpdateLayer()
err << "Unable to create layer for " << node->getName();
err << ", size " << info.width() << "x" << info.height() << " max size "
    << maxTextureSize << /* ... */;

메시지 속 WebView는 레이어를 할당하려던 RenderNode의 이름이다. hwui는 View 클래스 이름에서 패키지 접두사를 떼어 노드 이름으로 쓴다[1]. 레이어가 필요했던 주체는 WebView의 조상이 아니라 WebView 자신이었다.

Chromium 개발자도 이슈트래커에 같은 해석을 남겼다. 오프스크린으로 그려야 하는 뷰의 레이어 할당에 HWUI가 실패해 예외를 세우고, 이어서 WebView가 JNI로 Java를 호출하는 순간 그 예외가 Chromium 쪽에서 드러난다는 설명이다[2]. 스택이 WebView를 가리키는 것은 예외가 드러난 위치일 뿐이다.

크래시 데이터에서는 세 가지 단서가 더 나왔다.

막다른 가설 세 개

원인에 닿기 전에 세 가설을 지웠다.

  • 메시지가 사라졌다. 수집 파이프라인으로 집계한 데이터에는 해당 문구가 거의 없어서, 원인이 다른 것으로 바뀐 것처럼 보였다. 원본 이벤트를 직접 열자 최근 이벤트 전부에 같은 문구가 있었다. Caused by가 긴 네이티브 스택 뒤에 붙어 있어 텍스트 필드에서 잘린 것으로 판단했다.
  • 조상 뷰가 레이어를 만든다. 둥근 모서리 클립이나 회전 같은 조상의 속성도 하위 WebView를 레이어로 올릴 수 있다(다음 절에서 다룬다). ViewPager부터 Compose LazyColumn item까지 조상 경로를 전부 확인했지만 사각형 클립과 이동 변환뿐이었다. 노드 이름이 WebView라는 단서와도 맞지 않았다.
  • 라이브러리 업데이트 탓이다. 이슈트래커의 최초 보고자는 androidx.webkit 업데이트 후 빈도가 늘었다고 적었다. 우리 앱은 해당 기간 내내 같은 버전이었다.

정리하면, 레이어를 원한 것은 WebView 자신이고 Android 12 이상과 확대 상태가 조건이다.

레이어는 요청하지 않아도 생긴다

공식 문서는 LAYER_TYPE_NONE을 이렇게 정의한다.

"The view is rendered normally and is not backed by an off-screen buffer. This is the default behavior."[3]

이 문장은 개발자가 지정하는 레이어 타입에 관한 설명이다. hwui는 그와 별개로, 특정 조건을 만족하는 RenderNode를 스스로 레이어로 올린다. Android 15 소스의 promotedToLayer()가 그 조건이다[4].

// libs/hwui/RenderProperties.h (android15-release)
bool promotedToLayer() const {
    return mLayerProperties.mType == LayerType::None && fitsOnLayer() &&
           (mComputedFields.mNeedLayerForFunctors ||
            mLayerProperties.mImageFilter != nullptr ||
            mLayerProperties.getStretchEffect().requiresLayer() ||
            (!MathUtils::isZero(mPrimitiveFields.mAlpha) && mPrimitiveFields.mAlpha < 1 &&
             mPrimitiveFields.mHasOverlappingRendering));
}

첫 조건이 mType == LayerType::None이다. 개발자가 NONE을 지정한 노드에만 적용되는 규칙이라는 뜻이다. NONE은 "레이어 없음"보다 "레이어 여부를 hwui에 맡긴다"에 가깝다. 나머지 네 조건은 다음과 같다.

조건켜지는 때흔한 예
functor용 레이어WebView 같은 functor 노드가 복잡한 클립이나 변환 아래 그려질 때조상의 둥근 모서리 클립, 회전
ImageFilterRenderEffect를 설정했을 때blur
StretchEffectAndroid 12 stretch overscroll이 걸렸을 때스크롤 끝에서 당기기
alpha < 1겹쳐 그리는 노드가 반투명일 때페이드 애니메이션

1편의 실험에서 WebView에 투명도를 줬을 때 레이어가 생긴 것은 네 번째 조건이다. 이번 크래시는 세 번째 조건이었다.

stretch가 WebView 자신에게 걸리는 경로

Android 12부터는 스크롤 끝에서 당기면 화면 내용이 늘어났다가 돌아온다[5]. 늘어나는 연출은 이미 그린 내용을 변형해야 하므로, hwui는 대상 노드를 먼저 오프스크린 레이어에 그린 뒤 그 레이어를 늘려 합성한다. 어느 노드를 늘릴지는 EdgeEffect.draw()가 정한다[6].

// core/java/android/widget/EdgeEffect.java (android15-release)
} else if (edgeEffectBehavior == TYPE_STRETCH && canvas instanceof RecordingCanvas) {
    // ...
    RecordingCanvas recordingCanvas = (RecordingCanvas) canvas;
    // ...
    RenderNode renderNode = recordingCanvas.mNode;
    // ...
    renderNode.stretch(/* ... */);

mNode는 지금 녹화 중인 캔버스의 주인, 즉 onDraw()를 실행 중인 View의 RenderNode다. WebView는 자기 onDraw() 안에서 Chromium의 AwOverScrollHelper로 EdgeEffect를 그린다[7]. 그래서 stretch는 WebView 자신의 노드에 걸리고, 그 노드는 promotedToLayer()의 세 번째 조건을 만족한다.

크래시까지의 호출 경로

확대 상태에서 가장자리 드래그 → AwOverScrollHelper.onDraw() → EdgeEffect.draw() → WebView의 RenderNode.stretch() → promotedToLayer() 참 → WebView 크기의 레이어 할당 → 실패

평소에는 이 경로를 타지 않는다. 상품설명 WebView는 높이가 콘텐츠를 따라 늘어나는 WRAP_CONTENT라서 자체 스크롤 범위가 없기 때문이다. 문제는 핀치줌이었다.

// 핀치줌 터치 리스너 (발췌): 확대 상태에서는 부모의 가로채기를 막고 높이를 실측값으로 고정
if (isZoomed || event.pointerCount >= 2) {
    view.parent?.requestDisallowInterceptTouchEvent(true)
    if (webView.layoutParams?.height == ViewGroup.LayoutParams.WRAP_CONTENT && webView.height > 0) {
        webView.updateLayoutParams { height = webView.height }
    }
}

확대하면 WebView는 높이를 고정한 채 내부 스크롤을 시작한다. 이 상태로 좌우 끝까지 끌면 WebView 자신의 stretch가 동작한다. 핀치줌 적용 범위를 넓힌 시점과 크래시가 늘어난 시점이 겹친 이유다.

정리하면, NONE 노드도 stretch가 걸리면 레이어가 되고, 확대한 WebView는 스스로 stretch를 건다.

검사는 16383, 할당은 16384

승격 조건에는 fitsOnLayer()가 함께 걸려 있다. 노드가 텍스처 한도를 넘으면 승격하지 않는 안전장치다. 문제는 이 검사와 실제 할당이 서로 다른 높이를 본다는 점이다.

// RenderProperties.h: 승격 전 검사는 실제 높이로
bool fitsOnLayer() const {
    return mPrimitiveFields.mWidth <= deviceInfo->maxTextureSize() &&
           mPrimitiveFields.mHeight <= deviceInfo->maxTextureSize();
}

// SkiaGpuPipeline.cpp createOrUpdateLayer(): 할당은 64(LAYER_SIZE)의 배수로 올려서
const int surfaceWidth  = ceilf(node->getWidth()  / float(LAYER_SIZE)) * LAYER_SIZE;
const int surfaceHeight = ceilf(node->getHeight() / float(LAYER_SIZE)) * LAYER_SIZE;

한도가 64의 배수인 단말(16384, 32768)에서는 두 값이 같은 결론을 낸다. 한도가 16383인 단말에서는 그 사이에 63px짜리 틈이 생긴다. 메시지의 너비 1088도 같은 규칙으로 나온 값이다(1080을 64의 배수로 올림).

그렇다면 16384px보다 큰 WebView는 더 위험할까? 표를 보기 전에 한 번 예측해 보자.

WebView 높이 (한도 16383)fitsOnLayer()할당 높이결과
~16320px통과16320 이하레이어 생성, 정상
16321~16383px통과16384할당 실패, 크래시
16384px 이상실패할당 안 함레이어 없이 그림, 정상

답은 반대다. 한도를 넘는 WebView는 검사에서 걸러져 레이어를 만들지 않으므로 터지지 않는다. 위험한 것은 한도 바로 아래의 좁은 띠뿐이다. 하루 몇 건 수준으로 드물게, 그러나 꾸준히 발생한 이유도 여기에 있다.

한도를 넘는 WebView는 어떻게 그려지나

1만6천 px가 넘는 콘텐츠는 텍스처 한 장에 담기지 않는데, 어떻게 화면에 나올까. 평소의 WebView는 View 크기의 텍스처를 만들지 않는다. hwui는 WebView 차례가 오면 창의 프레임버퍼와 화면에 보이는 클립 영역을 Chromium에 넘기고(draw functor), Chromium은 콘텐츠를 작은 타일로 잘라 보이는 영역 근처만 래스터화해 합성한다. 그려지는 양은 콘텐츠 높이가 아니라 화면 크기다.

텍스처 한 장이 필요한 것은 레이어로 그릴 때뿐이다. 노드가 한도를 넘으면 hwui는 레이어를 포기하고 그대로 그린다[8]. 대신 레이어를 전제로 하는 효과는 빠진다. 기본 stretch 모드는 레이어 스냅샷에 셰이더를 입히는 방식이라, 한도를 넘는 WebView에서는 늘어나는 연출이 그려지지 않는다.

1편 다시 읽기

보충. 1편에서 본 "한도 이하는 한 번에, 초과하면 타일로" 그려지는 현상은 맞다. 다만 이 전환을 정하는 쪽은 Chromium이 아니라 hwui다. 1편 실험처럼 투명도 때문에 레이어가 필요해지면, hwui의 판단에 따라 WebView가 그려지는 곳이 달라진다.

WebView 높이hwui 판단WebView가 그려지는 곳Chromium이 래스터화하는 범위
한도 이하레이어 생성WebView 크기의 레이어콘텐츠 전체 (한 번에)
한도 초과레이어 포기화면보이는 영역 근처 (타일)

Chromium은 hwui가 넘겨준 그리기 영역의 크기를 그대로 따를 뿐이다[9].

정정. 1편은 LAYER_TYPE_NONE으로 레이어 경로를 우회했다고 결론 냈다. 실제로 끈 것은 하드웨어 레이어뿐이었고, 자동 승격 경로는 그대로 남아 있었다.

정리하면, 크래시 조건은 "승격 조건 하나 + 높이 16321~16383px + 한도 16383 단말"의 조합이다.

한 줄 수정: WebView의 stretch를 끈다

조합의 세 요소 중 앱이 고를 수 있는 것은 승격 조건뿐이다. 높이는 콘텐츠가 정하고, 한도는 단말이 정한다. 그래서 WebView가 stretch를 걸지 않게 했다.

WebView(context).apply {
    layoutParams = FrameLayout.LayoutParams(MATCH_PARENT, WRAP_CONTENT)
    isFocusableInTouchMode = false
+   overScrollMode = View.OVER_SCROLL_NEVER
    webViewFacade.initWebView(this, View.LAYER_TYPE_NONE)
    // ...
}

Chromium은 이 값을 받으면 stretch를 그리는 객체 자체를 만들지 않는다[10].

// android_webview/java/src/org/chromium/android_webview/AwOverScrollHelper.java
public void setOverScrollMode(int mode, Context context) {
    if (mode == View.OVER_SCROLL_NEVER) {
        mOverScrollGlow = null;
    } else {
        mOverScrollGlow = new OverScrollGlow(context, mContainerView);
    }
}

mOverScrollGlow가 null이면 그리기와 당김, fling 흡수 처리가 모두 건너뛰어진다. 스크롤 경계 계산은 달라지지 않는다. WebView는 View.overScrollBy()에 최대 오버스크롤 거리를 항상 0으로 넘기고, 프레임워크에서 overScrollMode가 바꾸는 값이 바로 그 최대 거리이기 때문이다. 사용자에게 보이는 차이는 다음과 같다.

상황수정 전수정 후
확대 후 가장자리 드래그WebView 내용이 늘어남가장자리에서 멈춤
1배 상태 세로 스크롤 끝바깥 LazyColumn이 늘어남동일
웹 페이지 내부 스크롤 영역Chromium 내부 처리동일

잃는 것은 확대 상태의 가장자리 연출 하나다. 한도를 넘는 긴 콘텐츠에서는 그 연출마저 원래 그려지지 않았다.

다른 선택지

한 줄 수정이 근본 해결은 아니다. 승격 조건 하나를 끈 것이고, 큰 WebView라는 구조는 그대로다. 검토한 선택지를 함께 적는다.

선택지효과판단
높이를 MATCH_PARENT로없음. LazyColumn item 안은 세로 제약이 무한대라 AndroidView가 UNSPECIFIED로 측정하고, WebView는 여전히 콘텐츠 높이로 커진다[11]채택 안 함
높이를 뷰포트로 고정노드가 화면 크기로 줄어 승격 조건과 무관하게 이 결함 계열이 사라진다근본 해결. LazyColumn과 WebView 사이 스크롤 연결과 콘텐츠 높이에 의존하는 로직을 다시 만들어야 해 별도 과제로 남김
위험 구간 회피 보정높이를 16321~16383px 밖으로 조정단말별 한도 조회가 필요하고 다른 승격 조건은 막지 못함
upstream 수정 대기이슈트래커에 보고돼 있으나 수정 계획 없음결함이 시스템의 libhwui에 있어 고쳐져도 OS 업데이트로만 배포됨

1편은 한계 절에서 "match_parent 또는 고정 높이 정책"을 바람직한 방향으로 적었다. 확인해 보니 스크롤 컨테이너 안에서 match_parent는 효과가 없고, 근본 해결은 고정 높이 쪽이다.

실기기로 확인한 세 가지 초록

소스만으로는 hwui가 실제로 WebView를 승격하는지 확정할 수 없다. maxTextureSize가 16383인 Galaxy S21에서 개발자 옵션의 "하드웨어 레이어 업데이트 표시"를 켰다. 레이어가 갱신되는 영역을 초록색으로 깜빡여 보여 주는 옵션이다. 수정 전과 후 빌드를 번갈아 설치해 같은 동작을 반복했다.

조건관찰해석
수정 전, 확대 후 좌우 끝WebView 영역만 초록WebView 노드가 stretch로 승격된다
수정 후, 같은 동작초록 없음승격 경로가 끊겼다
세로 스크롤 맨 위와 맨 아래리스트 영역 초록LazyColumn의 stretch 레이어. 뷰포트 크기라 한도와 무관하다
수정 전, 한도를 넘는 긴 콘텐츠초록도 stretch도 없음fitsOnLayer() 실패로 레이어를 포기했다

마지막 행은 미리 세운 예측을 시험한 결과다. 소스대로라면 한도를 넘는 WebView는 승격되지 않아 초록이 없어야 하고, 기본 stretch 모드는 레이어가 필요하니 늘어나는 연출도 사라져야 한다. 두 가지 모두 그대로 관찰됐다.

세로 끝의 초록은 Compose가 stretch를 위해 따로 만드는 RenderNode다. foundation의 StretchOverscrollNode는 리스트 내용을 뷰포트 크기의 노드에 녹화한 뒤 그 노드에 stretch를 건다[12]. 레이어는 생기지만 화면 크기라서 64의 배수로 올려도 한도에 닿지 않는다.

아직 확인하지 않은 것
  • 콘텐츠 높이를 재지 않았다. 표의 "한도를 넘는 긴 콘텐츠"는 콘텐츠 길이로 추정한 분류다.
  • 16321~16383px 구간에서 크래시를 직접 재현하지는 않았다. 수정은 높이와 무관하게 승격 자체를 막으므로, 인과 근거로는 위 관찰이면 충분하다고 판단했다.
  • 이 글을 쓰는 시점에 수정은 배포 전이다. 실사용 크래시 지표는 배포 후에 확인한다.

교훈

  • 1LAYER_TYPE_NONE은 "레이어 없음"이 아니다. hwui는 stretch, alpha, RenderEffect, 복잡한 클립 아래의 functor 조건에서 NONE 노드를 스스로 레이어로 올린다.
  • 2콘텐츠 높이만큼 큰 View에는 레이어를 부르는 효과를 두지 않는다. 스크롤 컨테이너 안의 WRAP_CONTENT WebView가 대표적이다.
  • 3크래시 메시지의 노드 이름을 읽는다. "Unable to create layer for X"의 X가 레이어의 주인이다.
  • 4집계 데이터가 원인이 바뀌었다고 말하면 원본 이벤트부터 연다. 긴 네이티브 스택 뒤에 붙는 Caused by는 잘리기 쉽다.

스크롤 컨테이너 안에 WebView를 넣고 있다면 두 가지를 확인해 보자. 높이가 콘텐츠를 따라 커지는지, 그리고 그 WebView에 overscroll, alpha, RenderEffect나 둥근 클립이 걸릴 여지가 있는지다. 둘 다 해당하면 개발자 옵션 하나로 바로 확인할 수 있다. 초록색으로 깜빡이는 영역이 WebView 전체라면, 그 WebView는 한도 근처의 높이를 만나는 순간 같은 크래시를 낸다.
